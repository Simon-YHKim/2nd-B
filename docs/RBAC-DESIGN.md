## 1. 지금 권한이 어떻게 결정되는가 (실측)

새 체계를 얹기 전에, **이미 있는 것**을 알아야 한다. 권한 판정은 지금 **세 곳**에 흩어져 있다.

| 어디 | 무엇으로 | 예 |
|---|---|---|
| `effective_subscription_tier(uuid)` | `users.judge_mode` → `brain`, 만료 → `free`, 그 외 `subscription_tier` | 프록시 3종의 프리미엄 게이트·일일 상한 |
| `billing_request_role()` | `request.jwt.claims` JSON 의 `role` | `service_role` 전용 함수 가드 |
| RLS 정책 | `auth.uid()` | 행 소유권 |

**이미 JWT 클레임을 읽는 관습이 있다**(`billing_request_role`). 새 역할도 같은 자리로 들어가는
것이 자연스럽고, 함수마다 테이블을 다시 조회하지 않아도 된다.

⚠ **0112 사고를 반복하지 말 것.** `request.jwt.claim.role`(단수 GUC)은 더 이상 설정되지 않는다.
`request.jwt.claims`(JSON) 를 읽어야 한다. 새 가드는 **`billing_request_role()` 을 확장하거나
같은 방식으로 읽는 헬퍼**를 쓰고, 인라인 `current_setting` 을 새로 쓰지 않는다.

## 2. 역할 정의

세 축이 섞이지 않게 **분리**한다. 이게 이 설계의 핵심 결정이다.

| 축 | 값 | 어디에 저장 | 누가 바꾸나 |
|---|---|---|---|
| **직무 역할** | `admin` · `developer` · `support` · (기본 없음) | 새 `user_roles` | 사람(운영자)만 |
| **요금 등급** | `free` · `cortex` · `polaris` | 기존 `users.subscription_tier` | 결제 웹훅만 |
| **comp** | 무상 상위 이용 | 직무 역할에서 **파생** | 사람만 |

**왜 합치지 않나.** 등급은 결제 이벤트가 자동으로 쓰고, 직무 역할은 사람이 준다. 한 컬럼에
섞으면 **웹훅이 운영자 권한을 덮어쓰거나 지우는 사고**가 구조적으로 가능해진다. 지금
`judge_mode` 가 정확히 그 형태로 등급을 우회하고 있었고, 그래서 `0138` 에서 컬럼 쓰기를 막았다.

### 각 역할이 할 수 있는 것 (초안)

| | admin | developer | support | 일반 |
|---|---|---|---|---|
| 자기 데이터 | ✔ | ✔ | ✔ | ✔ |
| 남의 개인 데이터 열람 | **✖** | **✖** | **✖** | ✖ |
| 운영 지표·집계(비식별) | ✔ | ✔ | ✔ | ✖ |
| 신고·차단 처리(커뮤니티) | ✔ | ✖ | ✔ | ✖ |
| 개발자 화면(`/dev-screens`) | ✔ | ✔ | ✖ | ✖ |
| comp(무상 상위 이용) | ✔ | ✔ | ✖ | ✖ |
| 역할 부여·회수 | ✔ | ✖ | ✖ | ✖ |

⚠ **`admin` 도 남의 기록을 못 본다**가 이 표에서 가장 중요한 줄이다. 이 앱이 보관하는 것은
사람의 일기와 관계·건강 기록이고, "운영자니까 볼 수 있다"는 권한은 **한 번 열면 되돌릴 수 없다.**
운영에 필요한 것은 대체로 **집계**지 원문이 아니다. 원문 열람이 정말 필요한 사건(법적 요청 등)은
역할이 아니라 **별도 절차 + 감사 로그**로 다뤄야 한다. — **Simon 확인 필요 (D-1)**

## 3. 역할을 어디에 두고 어떻게 읽나

### 저장: `user_roles` 테이블 (권장)

```
user_roles(user_id uuid, role text, granted_by uuid, granted_at timestamptz, note text)
  PK (user_id, role)          -- 한 사람이 여러 역할을 가질 수 있다
  RLS: 본인 SELECT 만. INSERT/UPDATE/DELETE 는 service_role 전용
```

`users.role` 단일 컬럼 대신 테이블인 이유 셋:

1. **다중 역할**이 자연스럽다(`developer` 이면서 `support`).
2. **누가 언제 왜 줬는지**가 남는다. 권한은 회수보다 부여 기록이 중요하다.
3. `users` 는 이미 결제 웹훅이 쓰는 테이블이다. 권한을 거기 두면 2절의 분리가 깨진다.

### 읽기: custom access token hook → JWT 클레임

Supabase **Custom Access Token Hook**(무료)이 토큰 발급 시 `user_roles` 를 읽어
`app_roles: ["developer"]` 클레임을 심는다. 그러면 RLS·`SECURITY DEFINER` 가드가
**테이블 조회 없이** 클레임만 보면 된다.

```sql
-- 새 헬퍼. billing_request_role() 과 같은 방식으로 claims JSON 을 읽는다.
create or replace function public.has_app_role(p_role text) returns boolean ...
```

⚠ **토큰 수명만큼 지연된다.** 역할을 회수해도 이미 발급된 액세스 토큰은 만료까지 유효하다.
그래서 **회수가 즉시여야 하는 판정**(예: 차단된 운영자)은 클레임이 아니라 테이블을 봐야 한다.
초안: **부여는 클레임으로 빠르게, 회수는 테이블 확인이 필요한 경로에만 추가.** — **Simon 확인 필요 (D-2)**

## 4. `judge_mode` comp 의 대체

`0138`(REQ-260820-04)이 자동 플래그를 없애고 클라이언트의 컬럼 쓰기를 막았다. 컬럼과
`effective_subscription_tier()` 의 comp 분기는 **일부러 남겼다** — 여기서 받기 위해서다.

```sql
-- 승인 후: comp 를 역할에서 파생시킨다
WHEN exists (select 1 from user_roles r
              where r.user_id = u.id and r.role in ('admin','developer'))
  THEN 'polaris'
```

그러면 `judge_mode` 컬럼은 **삭제 대상**이 된다(별도 마이그레이션, 데이터 0행이라 안전).

## 5. 유출 비밀번호 차단 — Supabase Pro 없이

**Q-260819-01 은 이것으로 폐기 확정이다.** Supabase 의 leaked-password 기능은 Pro 플랜이지만,
같은 데이터(HIBP)를 **무료·키 불필요**로 쓸 수 있다.

### 방식: HIBP range API (k-anonymity)

```
SHA-1(password) = ABCDE1234...          -- 로컬에서 계산
GET https://api.pwnedpasswords.com/range/ABCDE      -- 앞 5자리만 전송
→ 같은 접두사를 가진 해시 접미사 수백 개 + 유출 횟수
→ 나머지 35자리를 로컬에서 대조
```

**원문도 전체 해시도 밖으로 나가지 않는다.** HIBP 는 어떤 비밀번호를 물었는지 알 수 없다.
키·계정·요금 없음.

### ⚠ 어디서 돌릴 수 있는가 — 정직한 한계

실측: 가입은 `supabase.auth.signUp`, 비밀번호 변경은 `supabase.auth.updateUser` 로
**둘 다 클라이언트 SDK 가 직접 호출**한다. 중간에 우리 엣지 함수가 없다.

| 안 | 강제력 | 비용 |
|---|---|---|
| **A. 클라이언트 사전 검사** (권장) | 조작된 클라는 우회 가능 | 작다. 화면 2곳 |
| B. 가입을 엣지 함수 뒤로 이동 | 서버 강제 | 크다. 인증 흐름 재작성 + OAuth 경로 재검토 |

**A 를 권한다. 이유는 위협 모델이다.** 유출 비밀번호 차단은 *사용자를 자신의 재사용으로부터*
보호한다. 우회하는 사람이 해치는 것은 **자기 계정뿐**이다. 인가(authz) 검사와 달리 우회의
피해자가 우회자 자신이므로, 클라이언트 검사로도 실제 위험은 거의 다 덮인다.
그래도 서버 강제가 필요하다고 보면 B 로 간다. — **Simon 확인 필요 (D-3)**

### 곁들여 (무료, 같은 PR 로 가능)

- **비밀번호 최소 강도** — 현재 화면 문구는 "8자 이상, 대소문자와 숫자를 섞으면 더 안전합니다".
  Supabase Auth 설정에서 최소 길이·문자 요구를 서버에서 올릴 수 있다(무료).
- **가입 이메일 확인** 이미 켜져 있음.

## 6. 도입 순서와 되돌리기

```
1. user_roles + RLS + has_app_role()          (아무도 역할이 없으므로 무해)
2. custom access token hook 등록               (클레임이 실리기 시작)
3. 가드 1곳을 클레임으로 전환 + 테스트          (완료조건 ③)
4. effective_subscription_tier comp 를 역할로   (judge_mode 대체)
5. judge_mode 컬럼 삭제                        (별도, 데이터 0행)
6. HIBP 검사 (가입·비밀번호 변경)               (완료조건 ②)
```

**되돌리기**: 1~3 은 역할이 0행이면 동작 변화가 없다 — 훅을 끄면 클레임이 사라지고 가드는
`false` 로 떨어진다(= 권한 없음, 안전한 방향). 4 는 comp 를 잃는 사람이 생길 수 있으므로
**역할을 실제로 부여한 뒤에만** 넘어간다.

**지금이 가장 싼 시점이다**: 유료 구독자 0명, comp 0명. 권한 체계는 되돌리기가 비싸므로
이 문서가 게이트인 이유이기도 하다.
