「오류 신고」와 「이메일 문의」(Z74) = 「앱 안 신고 양식(받는 서버 쪽 일이 필요)」.
장부: `docs/handoff/CODEX-TASK-LEDGER-261016.json` T53.

## 설계와 데이터

- 사용자가 쓴 글(1~2,000자), 앱 버전, 현재 화면 경로(`/support`), 화면 언어만 보낸다.
  이전 화면 이력·쿼리·식별자가 붙은 경로를 수집하지 않는다. 기록 원문·대화·위키는 자동 첨부하지 않는다.
- 접수 운영에 필요한 계정 UUID(서버 `auth.uid()`), 종류, 재시도 UUID, 접수 UUID,
  동의 판본(`support-v1`), 접수 시각을 함께 저장한다. 이름·메일·전화·나이·첨부파일을 추가 수집하지 않는다.
- 목적은 앱 이용 문의와 오류 처리다. 앱 운영자만 내용을 읽는다. LLM·광고·분석 이벤트로 보내지 않는다.
- 매 접수마다 선택 동의(기본 미선택). 거절해도 앱 사용은 가능하며 이 양식의 접수만 하지 않는다.
  동의 내용보기에서 항목·수신자·목적·보관·거부 결과와 실제 메타데이터를 확인한다.
- 가입이 완료된 성인·미성년에게 같은 동의와 수집 범위를 적용한다. 나이를 신고 표에 복사하거나
  나이에 따라 더 수집할 이유가 없다. 기존 C10 가입/프로필 관문을 그대로 쓰며 새 연령 예외를 만들지 않는다.
- 권장 보관 초안: 접수 30일 경과 후 매시간 삭제(정상 스케줄에서 최대 약 1시간 지연).
  계정 삭제 시 FK cascade로 지운다. 기록 전체 삭제는 신고·쿼터를 초기화하지 않는다.
- 계정당 최근 1분 2건, 최근 24시간 10건. 재시도는 기존 접수 번호를 반환하고 횟수를 더하지 않는다.
  가입된 계정이 필요하다. 이 제한은 계정별이며 여러 계정을 합친 IP 제한은 이번 범위에 없다.

## 화면과 실패

공식 [토스 접수 양식](https://support.toss.im/customer-complaint)의 내용 입력·수집 동의·접수 버튼 구성을 참고했다
(2026-10-24 확인). 토스의 연락처·생년월일 입력은 이 목적에 필요하지 않아 가져오지 않았다.
답변 받을 길을 알리는 관례는 따른다. 별도 연락처를 받지 않고 가입 이메일로 답장하며,
동의 전과 접수 완료 화면에 이를 표시한다. 앱 안 답변함은 없다.
기존 `DeepSpaceScreen`, `Input`, `Button`, 휴대폰 안 화면·뒤로가기·키보드 부품을 재사용한다.

`/support` 안에서 화면을 전환하므로 새 라우트와 딥링크는 없다. 두 진입은 각각 문의/오류로 구분된다.
`EXPO_PUBLIC_IN_APP_REPORTS`가 정확히 `true`일 때만 양식으로 간다. 미설정·false·잘못된 값은
기존 두 mailto URL을 그대로 쓴다. 배포 설정에는 값을 추가하지 않았다.

오프라인이면 접수하지 않고 다시 시도를 보여 준다. 연결 확인과 RPC 각각 최대 15초다.
접수 UUID를 받은 경우에만 「보냈습니다」와 번호를 표시한다. 네트워크 오류·시간 초과는
「접수 결과를 확인하지 못했습니다」로 구분한다. RPC가 나간 뒤 글/동의는 잠그고,
일시 오류의 다시 시도는 같은 봉투를 보낸다. 늦은 응답이 있더라도 두 번 접수되지 않는다.
입력·길이·권한·RPC 부재 등 명시적인 영구 거절은 같은 요청을 재전송하지 않고 기존 이메일 문의를 연다.
전송 전 입력 검사는 글을 고쳐 다시 보낼 수 있다. 공백만 있는 글은 앱과 서버 모두 거절하며,
서버 RPC와 표 CHECK는 JavaScript trim의 공백 문자 집합(줄바꿈·탭·U+3000 포함)을 명시한다.
연속 누름은 동기 상태로 막으며 서버도 요청 UUID에 유일 제약을 둔다.
화면을 떠나거나 앱을 닫으면 글·재시도 키를 버린다. 자동 재전송·영속 큐는 없다.
계정이 바뀌면 양식을 새로 만들고, 전송 직전과 결과 표시 직전에 기존 계정인지 확인한다.

## 서버·삭제·내보내기

`db/migration-drafts/UNNUMBERED_support_reports.sql`은 적용되지 않는 번호 없는 초안이다.
직접 INSERT/SELECT/UPDATE/DELETE 권한과 클라이언트 RLS 정책은 모두 닫혀 있다.
본인 쓰기는 `submit_support_report` SECURITY DEFINER RPC 한 곳만 열며 소유자 인자를 받지 않는다.
내용·종류·동의·메타데이터 키/타입/값 검사를 서버에서 다시 한다. 반환은 접수 UUID 하나다.
계정 행 잠금 뒤 서버 시각으로 분/일 한도를 검사하므로 동시에 들어온 요청도 같은 한도를 쓴다.
Edge와 외부 전송은 필요 없다. 운영자는 service role로 읽고, 일반 사용자는 원문을 다시 읽을 수 없다.

초안이 삭제 등록부에 `account_delete_only`를 등록한다. 운영 정본 JSON은 아직 없는 표를
있다고 주장하지 않도록 그대로 둔다. `support-reports.inventory.json`이 초안의 삭제/내보내기 분류이며,
새 시험이 이를 실제 내보내기 분류 검사에 겹쳐 넣어 누락/중복을 막는다.
`PENDING`은 영구 제외가 아니다. 번호 부여 때 정본 등록부와 생성된 forward,
`export-account`의 PENDING 분류로 옮기고, 활성화 전 본인 신고의 내용·메타데이터·시각·번호·동의 판본을
내보내도록 구현/배포한다. 사용자 화면에 대한 SELECT 권한을 열어 내보내기를 해결하지 않는다.

## 개인정보 처리방침과 적용 순서

현행 `docs/legal/privacy-policy.md` §1·2·3에는 이 접수 데이터·목적·30일 주기가 명시돼 있지 않으므로
새 항목이 필요하다. **게시 PR은 서버 적용 뒤**이며 이 PR은 방침 원문이나 게시물을 바꾸지 않는다.
현행 §3의 소비자 불만·분쟁처리 기록 3년 조항과 일반 기술 문의의 30일 초안 구분은
게시 전 법무 검토에서 확정해야 한다. 이 초안은 법정 보관 대상까지 30일로 줄인다는 판단이 아니다.
범위를 확정하기 전에는 `support-v1`을 게시하거나 스위치를 켜지 않는다.

1. 독립 검토 PASS·새 medium 0·CI 초록 후 코디네이터가 휴면 PR을 머지한다.
2. 후속 PR에서 번호 부여·초안 제거·삭제/내보내기 정본 분류를 함께 한다. 기존 번호는 고르지 않는다.
3. Relay가 적용하고 실제 RLS/ACL·계정 삭제·동시 요청·활성 pg_cron 주기와 첫 정리를 확인한다.
4. 본인 신고 내보내기를 배포·확인하고, 처리방침·동의 문구 법무 검토 및 별도 게시 PR을 완료한다.
   운영자가 접수 목록을 확인하고 응답하는 절차도 확인한다. 기존 C11 응답 기준은 바꾸지 않는다.
5. 앱·웹·APK 공통 빌드 설정에 명시적으로 `EXPO_PUBLIC_IN_APP_REPORTS=true`를 반영한다.
   되돌릴 때는 false/unset으로 다시 빌드해 기존 메일 경로를 쓴다. 신고 원문을 지우는 롤백은 하지 않는다.

8081 확인은 코디네이터가 맡는다: OFF 두 메일 경로, ON 문의/오류 제목, 키보드·뒤로가기,
5개 언어·동의, 오프라인 실패, 응답 유실 후 같은 번호, 중복 누름 1건, 한도, 계정 전환.
이번 구현 세션은 8081·운영·QA 로그인·배포·스위치 변경을 하지 않는다.
