# 큰 재설계 실행 로드맵 · T69~T76

작성: 2026-10-15 · 코드 대조 기준: `84eae1a87f46ccb24bbcb8df5ab65e61a1862f4d` (`origin/main`, T68 측정 준비 #2548 포함).

이 문서는 Q-261015-85에 따라 큰 재설계의 순서·의존성·완료 증거를 분리한다. **로드맵 작성은 T69~T76 여덟 기능의 구현 완료가 아니다.** 현재 안전·보안·인터뷰·화면 큐를 먼저 끝낸다. T68 Claude 텍스트 생성·OCR 전환의 좌석별 측정은 Q-261015-86으로 따로 승인된 선행 예외다. 두 결정 모두 [10-15 확정 답](../../DECISIONS.md#L98)을 따른다.

T 번호는 [원 인수표](https://github.com/Simon-YHKim/2nd-B/blob/faec39fb6167ab0dad5df5dfea5ce12742567ce3/docs/HANDOFF.md#L136)의 묶음 번호다. T68의 별도 [측정 준비 문서](claude-seat-measurement-261015.md)는 좌석 인벤토리·비교 계약·실측 선행 조건을 다룬다. 아래의 현재 상태는 저장소 코드와 결정 기록을 읽어 대조한 결과다. 운영 DB 적용, 실행 중인 서버 설정, 실제 모델 품질, 폰 동작을 새로 확인했다는 뜻이 아니다. 이 문서 작업의 운영 변경·모델 호출·비용은 모두 0이다.

## 순서와 병렬 작업 경계

원 재설계의 [단계 순서](../../DECISIONS-2026-10-07_12.md#L47)는 `S0 → H1 → S0.5 → (S1·R·S2·S6a 병행) → W → S3 → E → S4 → L → S5 → S6b → S7`, `S8은 R 뒤 병행`이다. T 번호 하나에 여러 단계가 섞여 있으므로 T69부터 T76까지를 한 줄로 직렬 실행하지 않는다. 아래는 그 선후 관계를 현재 큐에 붙인 실행 분해다. 새 제품 승인을 뜻하지 않는다.

## T69 · 남은 생성 좌석과 라우팅 정리

**현재: 일부 구현.** 선언만 있던 열 좌석의 제거는 [purpose 정의의 S0.5 기록](../../src/lib/llm/types.ts#L46)에 있다. 실제 `/ops`는 [라우트](../../src/app/ops.tsx#L8) → [버튼 실행 함수](../../src/screens/deepspace/dds-ops-screen.tsx#L549) → [버튼 연결](../../src/screens/deepspace/dds-ops-screen.tsx#L922)로 이어지며 `forceFresh: true`를 전달한다. [옛 OpsHomeScreen](../../src/screens/deepspace/ops/screens.tsx#L286)의 자동 실행은 살아 있는 화면 동작으로 세지 않는다.

그러나 [추천 엔진](../../src/lib/ops/recommend.ts#L155)의 일일 요약 경로, [`ops_daily_brief` 호출](../../src/lib/ops/daily-brief.ts#L194), [`audit_qa` 호출](../../src/lib/records/create.ts#L285), 목적·라우팅 선언은 아직 있다. “버튼이 있으니 좌석 은퇴도 끝났다”는 결론도 틀리다.

남은 단위:

1. 실제 라우트와 모든 `recommendForDomain` 호출자를 대조하고, 첫 진입·그룹 변경은 호출 0, 명시 버튼은 필요한 호출만 나감을 고정한다. 고아 화면을 다시 연결하지 않는다.
2. `ops_daily_brief`·`audit_qa`의 현재 소비자와 대체 동작을 정리한 작은 PR로 은퇴한다. 기존 기록 저장·고정 안전 안내·사용자 답은 계속 보존한다. purpose별 감사·쿼터의 과거 ID는 합치지 않는다.
3. xAI·Gemini 잔재는 설치된 구빌드·기본값·다른 소비자가 쓰는지 확인한 뒤 제거한다. 동결된 좌석의 삭제와 `ops_daily_brief` 표 삭제를 자동 실행하지 않는다.

**완료 증거:** 라우트에서 버튼까지의 호출 횟수 회귀, 은퇴 좌석의 도달 가능한 호출 0, 저장 성공/실패 및 위기 안내 보존, 목적별 감사·쿼터 회귀, 서버 설정·배포본 대조. 기존 `ops` 엔진·daily-brief·화면 회귀를 재사용하고 필요한 행동 사례만 보강한다.

## T70 · 새 입력 구조와 한 번 이관

**현재: 기존 저장 경로와 일부 D6 기반은 존재, 새 통합 구조는 미완료.** [captureFromMarkdown](../../src/lib/wiki/capture.ts#L76)은 중복 판정·본문 업로드·소스 저장을 한다. [링크 입력](../../src/app/capture.tsx#L2991)은 URL로 제목·본문을 만들며, 기사 본문 정적 수집과 실패 시 화면 OCR을 구현한 경로가 아니다. [D6 스키마](../../db/migrations/0225_interview_transcript_ledger.sql#L271)의 `ai_hold`·`superseded_by`는 인터뷰 대화록의 필드다. 이를 모든 입력의 버전·hold 계약 완료로 세지 않는다.

기준 코드의 `src`·`db/migrations`에서 테스트를 제외하고 `domain_primary`, `domain_suggested`, `ingest_channel`, `period_card_proposals`를 정확히 검색했을 때 구현 정의는 없었다. 이는 해당 명칭의 계약 부재를 확인한 것이며, 앱에 저장·분류 기능 자체가 없다는 뜻은 아니다.

확정 계약은 [D2~D11](../../DECISIONS-2026-10-07_12.md#L25)을 적용한다.

- 생활 영역은 여섯 중 하나 또는 `null`: `domain_primary`·`set_by`·`locked`·`domain_suggested`. 보조 영역을 새로 더하지 않는다.
- 입력 채널은 `interview`, `scrap`(memo/ocr/4w1h/link/file/voice), `journal`(일기·검사·북극성), `conversation`, `import`(서술형). 측정값은 `sync`, interaction은 이벤트이며 위키·레코드 본문에 넣지 않는다.
- 수정은 새 원문 버전과 `superseded_by`로 연결한다. 사용자가 삭제하면 과거 버전·파생물도 삭제 계약을 따른다. “불변 원문”은 삭제 거부의 이유가 아니다.
- 위기 글은 저장·고정 안내를 제공하되 AI 추출·임베딩·분류에서 제외하는 durable `ai_hold`를 모든 후속 읽기에 전파한다. D6의 인터뷰 hold만으로 일반 입력 전체가 막혔다고 하지 않는다.
- 링크 본문은 정적 수집, 실패 시 화면 OCR이다. 무료·상업 이용 조건과 서버 수집 경계를 먼저 확인한다. 외부 링크의 내부 주소 접근·리다이렉트·큰 응답·시간 제한·주입 텍스트를 검증한다.
- 링크 “저장 안 함”은 URL·제목·추출문·로컬 초안·공유 쿼리·로그인 전 대기열까지 사용자 원문 흔적을 없앤다. C3 감사 행은 원문 해시도 비워 보존한다. 공급자 보관은 별도 계약이며 앱 삭제가 공급자 삭제를 증명하지 않는다.

**완료 증거:** 다섯 채널과 측정값 분리의 고정 사례, 버전·삭제·hold의 모든 읽기 경로 시험, 저장 전 이탈·실패·재시도·계정 전환 뒤 흔적 검사, 링크 수집 실패와 OCR 대체 시험. 이관 직전 현재 계정·원문·파생물 수를 다시 세고 ID 대응·누락·중복·삭제·hold 대조표를 남긴다. 10-07의 “5계정·59기록”은 당시 수치이므로 실행 입력으로 고정하지 않는다. 검증된 준비·복구 절차 후 한 번 전환하고, 실제 적용과 읽기 확인 전에는 이관 완료가 아니다.

## T71 · 짧은 정체성 카드와 읽기 계층 R

**현재: 원문을 읽는 기존 길이 있고, R 통합과 새로운 동의 범위는 미완료.** [대화 엔진](../../src/lib/chat/conversation.ts#L240)은 구조화 기록·직접 적은 프로필·RAG·위키 내보내기를 이미 쓴다. [프로필 맥락](../../src/lib/persona/profile-context.ts#L17)도 있다. “대화가 위키를 안 읽는다”는 옛 진단으로 요약을 원문 대신 넣지 않는다.

대화의 `exportUserWiki` 호출은 `includeRecords`를 켜지 않는다. [내보내기 구현](../../src/lib/wiki/export.ts#L245)은 이 선택이 있을 때만 일기·메모 기록을 읽는다. 이것은 기존 개인정보 경계다. R은 [Q13](../../DECISIONS-2026-10-07_12.md#L35)·[RD02](../../DECISIONS-2026-10-07_12.md#L51)에 따라 **성인 + `long_term_memory` opt-in**일 때만 해당 원문을 대화 문맥에 넣고, 첫 대화/첫 저장의 명시 동의 안내를 갖춘다. 미성년 설정 키가 존재하는 것과 원문 전송 허용을 혼동하지 않는다.

남은 단위는 짧은 정체성 카드의 확정 필드·길이·갱신 근거, R의 소유자·동의·연령·hold·삭제·최신 버전 필터, 화면용 숫자와 모델용 원문 발췌의 분리다. 정체성 카드는 늘 싣는 짧은 안내이고 판단의 근거는 원문이다. 인터뷰의 새 질문은 [Q-261014-14](../../DECISIONS.md#L74)대로 이번 대화 안에서 고르며, R이 생겼다고 과거 저장 원문까지 자동 확대하지 않는다.

**완료 증거:** 성인/미성년/나이 미확인 × 동의 켬/끔, 계정 전환, 삭제·hold·옛 버전, RAG 실패 때 대체 읽기에도 같은 필터가 적용됨을 시험한다. 실제 조립된 요청에서 원문 인용과 짧은 카드의 범위, 흐름 2 숫자 제외를 확인한다. 기존 RAG·wiki export·profile-context·동의 시험을 이어 쓰고 새 계약의 빈틈만 보강한다.

## T72 · 달력 먼저, 건강 확장과 위치는 차례대로

**현재: 어댑터가 있지만 활성화·확장 완료와 다르다.** [폰 달력 읽기](../../src/lib/import/phone-calendar.ts#L152)는 있고 [활성화 스위치](../../src/lib/import/phone-calendar-gate.ts#L12)는 `false`다. [건강 자동 읽기](../../src/lib/health/auto-read-runner.ts#L5)는 전경에서만 돌며, [Health Connect 종류](../../src/lib/health/sources/health-connect.ts#L57)는 걸음·운동·수면·심박이고 거리는 없다. [HealthKit 어댑터](../../src/lib/health/sources/healthkit.ts#L44)는 존재하므로 “iOS 코드 없음”으로 세지 않는다. 설치된 네이티브 API와의 일치 및 실기 확인이 필요하다.

순서는 **달력 → Android 백그라운드 건강 + 거리 → iOS 건강 → 법·스토어 조건을 충족한 위치**다. 달력 읽기와 기존 일정 쓰기는 다른 권한·동의 경로다. 달력은 Q-27의 변경 고지·재확인과 별도 선택 동의, 한국어/영어 처리방침·법무 검토 뒤 켠다. 거부해도 기존 앱을 쓸 수 있어야 한다. 법무 시각이 지났다는 사실만으로 회신 완료나 활성화 허가로 세지 않는다.

백그라운드 건강 읽기를 이유로 앱 시작 때 불필요한 배터리 예외를 요구하지 않는다. 앱 얼림은 별도 [10-14 결정](../../DECISIONS.md#L75)이 다룬다. GPS 날씨는 10-17(토) 개인 테스트·약관/공개 조건 작업으로 별도 관리하며, 이것이 도착·출발 위치 자동화 전체의 승인이나 공개 완료는 아니다.

**완료 증거:** 달력 동의 거부·철회·OS 거부·다중 달력·계정 전환·재동의, 건강 종류별 읽기·철회·거리 단위·중복 제거·전경/백그라운드, Android/iOS 실제 모듈 빌드와 폰 확인. 필요한 스토어 데이터 신고·위치 약관/동의/기록 보관 및 백그라운드 정책 확인까지 항목별로 남긴다. 네이티브 완료는 웹 시험만으로 판정하지 않는다.

## T73 · 시기 카드 승인에서 북극성 카드까지

**현재: 별 L5 비준 경로는 있고, 시기 제안·결정 전체 원장은 미완료.** [현재 비준 화면](../../src/screens/deepspace/DeepSpaceDesignScreens.tsx#L2070)은 승인·거절 흐름과 `recordSevenTiers`를 쓴다. [현재 원장 요약](../../src/lib/persona/ratification-screen.ts#L129)은 승인된 항목 수를 제안 수로도 세며 별도의 pending/거절 원장을 갖지 않는다. “비준 기능 없음”도 “원장 완성”도 현재 코드와 다르다.

남은 단위:

1. 한 저장소에 시기 제안·승인·거절·“빗나간 곳 알려주기”와 사용자가 승인한 “그때의 나” 문장을 둔다. 사용자 피드백은 다음 인터뷰의 허용된 맥락 안에서만 쓰도록 Q-14와 함께 설계한다.
2. 승인된 시기의 원문 인용만 역할 카드에 쓰고, 원문 삭제·hold·승인 철회 시 파생 카드·L5 근거도 함께 재검증한다. 요약 문장만으로 원문을 대체하지 않는다.
3. [RD-261007-13](../../DECISIONS-2026-10-07_12.md#L119)으로 D6 1단계에서 분리한 `period_card_proposals`·decide/delete·서버 L5 쓰기를 별도 단계로 구현한다. `persona_narrative`는 B1 동결을 유지한다.

**완료 증거:** 제안 → 승인/거절/빗나간 곳 → 다시 읽기의 실제 왕복, 중복 승인·동시 요청·소유자 경계·삭제와 L5 회귀, 승인 문장과 인용 원문의 보존·철회 일치. 실제 원장에 없는 “모든 제안 이력” 수치를 보여 주지 않는다. 기존 비준 경로를 보존하면서 새 저장소의 서버/클라이언트 검증을 추가한다.

## T74 · 처리할 것 한 큐와 규칙 기반 위젯

**현재: W1 부품·계약은 일부 구현, 폰 알림·기기 메일 연동까지 완성된 것은 아니다.** [부품 레지스트리](../../src/lib/dashboard/parts.ts#L1)는 이미 있다. [데이터 계약](../../src/lib/dashboard/contract.ts#L95)은 알림 W2·메일 W3을 구분하지만 [현재 triage 입력](../../src/lib/dashboard/generation-input.ts#L42)은 `source: "app"`만 받는다. 출처 union에 `notification`·`mail`이 있다는 사실은 연결 구현의 증거가 아니다. [메일 파일 파서](../../src/lib/import/email.ts#L33)도 기기 IMAP 수집기와 다르다.

확정 범위는 [한 큐·출처 칩](../../DECISIONS-2026-10-07_12.md#L81), [iOS=기기 IMAP+앱 / 웹=앱](../../DECISIONS-2026-10-07_12.md#L84), [맞춤 위젯 규칙 제안+승인](../../DECISIONS-2026-10-07_12.md#L85)이다. 내용·순서는 규칙이 결정하며 LLM이 화면 배치를 만들지 않는다. 표시 조건은 데이터 최소량·최근성, 숫자는 R의 결정적 출력이다. 단축어는 2단계, 메일 전달 주소·Gmail OAuth는 보류한다.

알림·메일의 triage 입력은 [RD11](../../DECISIONS-2026-10-07_12.md#L110)대로 발신자·제목만이다. 본문 미리보기 200자를 임의로 되살리지 않는다. 최근 7일 미접속의 `daily_note` 생략과 아침 푸시 opt-in 예외는 [Q37](../../DECISIONS-2026-10-07_12.md#L86)를 구현·확인한다. 범용 규칙 엔진을 만들기 위해 W1을 새로 시작하지 말고 기존 W1의 동작과 보안 후속부터 이어 간다.

**완료 증거:** 플랫폼별 실제 지원 출처, 동의·OS 권한·보관 시간·철회·계정 전환, 발신자/제목만 나가는 조립된 요청, 중복 항목과 출처 칩, 빈 상태·한 출처 쏠림·위젯 승인 전후, 7일 경계와 푸시 예외. 기존 dashboard 계약·generation-input·부품 시험을 재사용한다. 메일·알림 모듈은 기기 확인도 필요하다.

30일·24시간·3회·1시간은 결정 당시 채택한 제안값이다. 실제 시험에서 바꿀 필요가 생기면 근거를 보고하며 임의 상수 변경으로 기존 결정을 바꾸지 않는다. 위치 신고는 [10-07 정정](../../DECISIONS-2026-10-07_12.md#L132)의 법적 전제를 재확인하되, 약관·동의·이용 기록을 첫날부터 갖춰야 한다는 조건과 현재 개인 테스트 범위를 유지한다.

## 완료 판정과 다음 담당자에게 넘길 증거

각 T 항목의 **설계·구현·검증·독립 검토·머지·서버 적용·앱 반영·폰 QA**를 따로 기록한다. 해당 없는 단계는 근거와 함께 표시한다. “문서 있음”, “테스트 PASS”, “main 머지” 한 가지로 기능 전체를 완료 처리하지 않는다.

1. 각 작은 PR은 문제와 끝나는 동작, 기존 검사 재사용 범위, 새 행동 사례, 정확한 커밋 SHA를 남긴다. `npm run verify`는 저장소의 기존 전체 검사 명령을 그대로 실행한다. 문서만 바뀌는 이번 PR을 위해 구현을 그대로 되풀이하는 새 테스트는 만들지 않는다.
2. CI 통과·독립 검토 PASS·새 중간 지적 0을 유지한다. 같은 PR이 3회 BLOCK이면 중단·보고한다. 기존에 다른 PR에 주어진 추가 회차 허용을 이 로드맵에 일반화하지 않는다.
3. 모델 변경은 같은 고정 자료·같은 실제 앱 지시문/후처리로 기존 설정과 후보를 비교한다. JSON 형식, 직접 109 안내 보존, 119/112 구분, 언어·연령, 비용·시간·한도·동의·감사를 함께 판정한다. 모델 원출력만 맞고 화면에 안내가 사라지는 결과는 통과가 아니다. 실제 모델 ID·서버 라우팅 확인 없이 제품 이름을 코드명으로 추측하지 않는다.
4. DB·서버·설정 적용이 있으면 적용 전후의 버전·동작·복구 증거를 남긴다. `main` 코드 존재를 운영 적용으로 적지 않는다. 앱 변경은 머지 → 8081 반영 → `app:parity`와 화면/행동 확인, 네이티브 변경은 같은 설정 APK·폰 확인까지 이어 간다.
5. 접근·법무·기기 조건이 남으면 무엇을 확인하지 못했는지 적는다. 비밀값을 보고서에 싣지 않는다. Q-85와 D1을 다시 물을 필요는 없다. S7 표 삭제처럼 원결정에 별도 확인이 명시된 일은 실행 직전 구체적인 변경·영향·복구안을 준비한 뒤 해당 절차를 따른다.

**이 문서가 넘기는 결과:** 바뀐 결정을 반영한 T69~T76의 실행 순서와 완료 기준. **아직 넘기지 않는 결과:** 여덟 기능의 구현 완료, T68 실제 품질 측정 완료, 운영 적용·새 APK·공개 출시 완료. 진행 원장과 사용자 보고서는 이 구분을 유지한다.
