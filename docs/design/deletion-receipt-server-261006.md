```
                                  │                                │
                                  │ 10분 안에 execute 없음            │ public.users(A) DELETE 트리거
                                  ▼                                │ (A 의 accepted · executing 전부)
                              abandoned                            ▼
                         (같은 번호 재사용 거절)                  completed ── owner_id=NULL,
                                                                   │          receipt_expires_at 설정
          executing 이 Auth 삭제 전에 실패 · 15분 초과(A 가 살아 있음)    │
                              ──────▶ failed                       ▼ (만료 뒤 pg_cron 이 삭제)
```

- `executing` 이 15분을 넘었는데 `public.users` 에 A 가 **아직 있으면** 조회 시점에 `failed` 로 확정합니다(게으른 확정). A 가 **없으면** 트리거가 이미 `completed` 로 바꿨어야 하므로, 그 경우는 `completed` + `sweeps.unrecorded=true` 로 확정합니다(삭제는 사실이고 정리 기록만 없음).
- 같은 계정의 두 번째 기기 요청은 자기 행을 따로 갖습니다. 트리거가 둘 다 완료로 바꾸므로 각 기기가 자기 번호로 영수증을 찾습니다(I3).
- 늦은 begin(D2A-R2-04 경합): begin 은 `public.users` 행을 `FOR UPDATE` 로 먼저 잠그고(0192 `begin_account_deletion:72-80` 과 같은 순서), 행이 없으면 아무것도 쓰지 않고 `account_gone` 을 돌려줍니다. 사용자 id 와 번호를 잇는 기록이 삭제 뒤에 다시 생기지 않습니다.

### 3.3 delete-account 흐름 (두 단계)

| 단계 | 요청 | 서버가 하는 일 | 응답 |
|---|---|---|---|
| begin | `POST {op:"begin", op_id}` + A 의 JWT | JWT 검증(지금 `index.ts:182-205` 그대로) → users 행 잠금 → `op_id` 가 처음 보는 번호인지 확인 → `accepted` 행 · `token_hash` 저장 | `{op_id, op_token}` (op_token = HMAC(pepper, op_id ‖ A ‖ created_at)) |
| execute | `POST {op:"execute", op_id, op_token}` + A 의 JWT | 증표 검증 · 소유자 일치 · `accepted` 이고 10분 안 → `executing` → **그 다음** `begin_account_deletion`(tombstone) → Storage → Auth 삭제 | `{deleted:true, op_id, sweeps}` 또는 409 진행 중(같은 번호로 재시도) |
| 재시도 | execute 를 같은 번호로 | 이미 `completed` 면 파괴 없이 영수증만 돌려줍니다. `executing` 이면 계정별 advisory lock 으로 직렬화 | 같은 응답 |

- 지금 앱(본문 `{}`)과의 호환: 옛 본문 `{}` 는 계속 받되 **작업 행 없이** 지금처럼 동작하고 응답에 `op_id` 가 없습니다. 새 앱은 begin 이 400(옛 Edge)이면 "서버 영수증 미지원"으로 표시하고 기존 흐름으로 갑니다. #2078 의 "400 이면 `{}` 로 한 번 재시도" 와 같은 생각이고, 이 창은 Edge 배포 뒤 닫힙니다.
- **F5 (서버 tombstone 영구 차단) 처리:** execute 가 Auth 삭제 **전에** 실패해 `failed` 로 확정되면, 같은 계정 advisory lock 아래에서 그 계정의 tombstone 을 지울지 Simon 이 정해야 합니다(10절 Q6). 0198 등록부가 tombstone 을 "의도적으로 남는다"고 적고 있어서(`db/migration-drafts/service-contract-erasure-entries.json:5-8`) 혼자 바꾸지 않습니다.

## 5. 클라이언트 울타리 상태 기계

**먼저, 서버 완료 전에 기기 쓰기를 막을 필요가 있나.** 지금 main 과 #2054 는 "Edge 호출 전에 기기 울타리를 확인한다"(`delete-bulk.ts:325-332`)를 지켰고, 그 울타리가 서버에 안 간 실패에서 영구히 남는 것이 F1 · F2 · F4 의 뿌리였습니다. 울타리의 목적은 **삭제된 계정의 기기 데이터가 정리 뒤에 다시 생기지 않게** 하는 것입니다(추론, `local-deletion-fence.ts:103-107` 주석). 그 목적은 "서버 완료 확인 → terminal 울타리(쓰기들과 같은 잠금 아래) → 정리" 순서만으로 지켜집니다. 서버가 지우는 동안 생긴 기기 데이터도 그 뒤의 정리가 지우기 때문입니다. 그래서 이 설계는 **서버 완료 전에는 쓰기를 막지 않습니다.**

```
 idle
  │ 사용자 확인
  ▼
 pending{op, owner}                 ← 메모만. 쓰기 안 막음. 키: account.deletionOp.v1:<owner>:<op>
  │ begin 성공 → op_token 을 메모에 저장하고 다시 읽어 확인
  │ begin 실패 · 거절 · 응답 유실 → 메모 지움 (증표가 없으면 execute 를 못 보내므로 안전)
  ▼
 armed{op, owner, op_token}         ← 메모 영속 확인 뒤에만 execute 를 보냅니다 (불변식)
  │ execute 응답 deleted:true
  │ execute 응답 유실 · 모름 → armed 유지, 다음 실행 · 로그인 화면 진입 때 서버 조회 ②
  │   ② completed → terminal 로
  │   ② failed · abandoned → 메모 지움 (계정은 살아 있음)
  │   ② 모름(네트워크 · 미배포 · 5xx) → 그대로 둠
  ▼
 terminal{owner}                    ← 되돌릴 수 없음. 기존 키 account.deletionFence.v1:<owner>
  │ 기기 정리 (Web Locks 없으면 결과 "unconfirmed", 메모를 남겨 다음 실행에 한 번 더)
  ▼
 done → (로그인한 계정이 없으면) /account-deleted#r=<op> → 메모 지움
        (다른 계정이 로그인해 있으면 영수증 이동 없이 메모 지움. 영수증 화면은 서버만 읽음)
```

| 상태 | 쓰기 막힘 | 풀리나 | 무엇이 다음으로 보내나 | 게이트 함정과의 관계 |
|---|---|---|---|---|
| pending | 아니오 | 지우면 끝 | begin 응답 | 프로세스가 여기서 죽어도 막힌 것이 없습니다(DEL-SAFE-01 소멸). 서버는 execute 없는 `accepted` 를 10분 뒤 포기로 확정합니다. |
| armed | 아니오 | 서버 확정 답으로만 | execute 응답 또는 조회 ② | "모름"은 지우지 않습니다(I5). 증표가 있으므로 서버 행이 항상 있고, 답은 완료 · 진행 중 · 실패 · 포기 중 하나입니다. |
| terminal | 예 | **아니오** | 없음 | 서버가 completed 를 확인한 뒤에만 들어갑니다(I7). 저장이 느리거나 실패해도 서버 작업은 이미 끝났으므로 F2 가 생기지 않고, armed 메모가 남아 다음 실행에서 다시 시도합니다. |

- **키는 작업마다 하나.** pending · armed 메모는 `<owner>:<op>` 키에 둡니다. #2078 r1 의 목록 덮어쓰기(D2A-08)와 #2054 의 소유자당 값 하나(DEL-SAFE-04) · 모르는 값 덮어쓰기(DEL-BL-04)가 생기지 않습니다. 기존 terminal 키(`account.deletionFence.v1:<owner>`, `local-deletion-fence.ts:14-15`)는 그대로 두어 구빌드도 terminal 만 읽습니다(DEL-SAFE-02 · DEL-BL-03 이 닫힌 방식과 같음).
- **Edge 뒤 부가 정리는 결과를 붙잡지 않습니다.** 메모 정리는 응답을 화면에 넘긴 뒤 별도로 하고, 실패해도 결과를 덮지 않습니다(DEL-BL-05 · DEL-G3-01).
- **세션 미상은 로그아웃이 아닙니다.** 복구 조회 · 영수증 표시는 `knownSignedOut()`(#2078 r2 에서 닫힌 방식)일 때만 합니다. 이미 시작한 백그라운드 복구는 로그인 · 세션 미상 전환 때 멈춥니다(astra r2 "세션과 sweep" 관찰).

### 5.1 Web Locks 없는 브라우저
