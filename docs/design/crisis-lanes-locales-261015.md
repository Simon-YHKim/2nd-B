# 위기 안내 3갈래와 추가 언어 · T23 설계

상태: 구현·검증 준비, 독립 검토 전. 기존 119·112 판정 부재와 es·pt·id 어휘 부재를
닫는 작업이다. 이 문서나 부분 PR을 게시 조건 충족으로 세지 않는다.

## 결정과 상충

- Q-261010-09 및 Q-261015-82: 상담·신체 응급·타인의 급박한 위협을 구분하고,
  게시 전 es·pt·id 위기 어휘까지 검증한다. 이번 전체 작업 지시에 포함된다.
- 예전 `hotline-lane-separation.test.ts`의 모든 자동 경로에서 119·112를 금지하는 규칙은
  최신 결정으로 대체한다. **자살·자해만으로 경찰 안내를 붙이지 않는 규칙은 유지한다.**
- SystemLocale은 en/ko 계약이다. 어휘 인식 언어를 늘리는 데 UI·동의·DB 계약 전체를
  다섯 언어로 바꾸지 않는다. 세 추가 언어의 safety/consent 문구는 기존 영어 사본 정책을 따른다.
- 한국어 UI가 한국에 있다는 증거는 아니고, 영어·스페인어·포르투갈어·인도네시아어도
  나라를 확정하지 않는다. 새 긴급 안내에 임의로 외국 번호를 배정하지 않는다.
- 서버는 0255 → 0258 적용 확인 뒤에만 재배포한다. 이번 어휘 수정도 그 순서를 따른다.

## 작업 단위

1. 추가 언어의 명시적 위기 표현: 어휘 정본과 실행 가능한 말뭉치를 먼저 만들고
   앱과 프록시의 동일 입력에서 같은 판정을 검증한다. 기존 EN/KO 판정·문맥 예외는 유지한다.
2. 긴급 갈래: 현재 진행 중인 신체 위험과 피해자의 급박한 위협 진술을 별도로 판정한다.
   단어 하나로 가해자·범죄·질병을 추정하지 않는다. 이미 정해진 상담 갈래의 red를
   새 규칙이 green으로 낮추지 않는다. 불확실한 갈래는 상담 안내를 유지한다.
3. 화면·서버 연결: 판정 결과의 갈래를 고정 안내문과 실제 안내창까지 전달한다.
   서버 422는 폐쇄된 갈래 값만 반환하며 입력 원문·매칭 어휘를 내보내지 않는다.
   이전 서버의 갈래 없는 422도 기존 고정 안내로 안전하게 처리한다.
4. 지연·한도·저장: #2524의 즉시 안내와 #2525의 계정 소유 안내창에서도 같은 갈래를
   보존한다. 입력·감사 지연·답변 교체·기록 저장·임베딩·대시보드 입력을 각각 검사한다.

## 수용 검사

- 언어마다 실제 위기 표현과 평범한 대조문을 함께 둔다. 직접·간접 진술, Unicode·줄바꿈,
  혼합 언어, 부정문, 작업·웃음 같은 비유, 인용·지난 기록의 문맥을 구분한다.
- 상담 문장에는 112를 붙이지 않는다. 신체 응급이 명시되면 일반 대화 모델 호출 없이
  긴급 안내를 먼저 보인다. 타인 위협은 피해·현재성·급박함 근거가 있어야 한다.
- 한국의 상담은 성인 109·미성년 1388/109를 유지한다. 한국의 긴급 번호는 119·112다.
  나라를 확인하지 못한 경우의 안내는 국가를 지어내거나 빈 tel 링크를 만들지 않아야 한다.
- 정본과 gemini·공유 프록시·dashboard 입력 검사의 판정 결과를 대조한다. 단순 문자열
  동일성 외에 실제 실행에서 모델 호출 0·감사 시도·계정 전환 뒤 응답 폐기를 확인한다.
- 임의의 새 허용 문맥을 기존 예외 목록에 추가하지 않는다. T26의 닫힌 목록 및 법무 검토
  조건을 유지한다. 새 언어의 비유 처리도 검토 근거 없이 허용 예외로 숨기지 않는다.
- 실제 프롬프트를 바꾸는 경우에는 실제 모델 측정을 한다. deterministic fixture 통과를
  실제 모델 측정 또는 사람의 번역 검토로 보고하지 않는다.

## 기준 main 404a906e에서 확인한 공백

`classifyInputAnyLocale`은 현재 en/ko만 검사한다. 다른 UI 언어는 systemLocaleFor에서
영어로 바뀌므로 UI 팩을 추가한 것만으로 해당 언어의 위기 문장이 잡히지 않는다.
`routeCrisis`와 `fixedCrisisResponse`는 판정 결과와 무관하게 상담 번호를 다시 고른다.
따라서 분류기에 119/112만 더하면 안내문과 안내창이 다른 번호를 보일 수 있다.
`CrisisRouter`도 현재 상담 문구와 통화 버튼만 가지므로 긴급 갈래 연결과 함께 수정해야 한다.

대시보드는 `_shared/llm-input-safety.ts`를 통해 앱 판정을 실행한다. 나머지 프록시는
자체 어휘 사본을 쓰며 422에 갈래가 없다. 서버 사본·응답 계약·클라이언트의 해석을
함께 검사하고, 운영 반영 전에는 아직 T23이 완료되지 않았음을 원장에 남긴다.


## 첫 구현: 세 추가 언어의 명시적 표현

- 어휘 정본 `lexicon.ts`에 es·pt·id 각 7개, 합계 21개를 둔다.
  `crisis-language.ts`는 NFKC·대소문자·악센트·공백을 정규화하고 Unicode 단어 경계를 검사한다.
  UI 언어가 en/ko 어느 쪽이든 입력·출력·임베딩의 기존 `classifyInput` 호출에서 인식한다.
  UI 언어 또는 문장의 언어를 나라로 변환하지 않는다. 번호 선택은 기존 정책을 유지한다.
- 공유 프록시와 Gemini는 앱과 **같은 모듈·같은 어휘**를 import한다. 대시보드의 재귀 입력
  검사도 같은 분류기를 실행한다. Deno import map을 함께 갱신했다.
- 준비 단계의 직접 부정어 자동 제외 후보는 활성화하지 않았다. `No quiero suicidarme`,
  `Eu não quero me matar`, `Saya tidak ingin bunuh diri` 같은 부정문, 인용·지난 기록도
  일치하는 표현이 있으면 red다. 이는 알려진 과잉 판정이며 일반 문장을 정확히 이해한다는
  주장이 아니다. 새 허용 예외를 추가하려면 T26의 닫힌 목록·의견·검증 조건을 따른다.
- EN/KO의 기존 문맥·띄어쓰기 규칙은 변경하지 않았다. 새 인식어를 원문으로 감사에
  저장하지 않고 기존 제한된 category만 사용한다.
- 서버 배포·119/112 안내·실제 앱 확인은 이 어휘 변경만으로 완료되지 않는다.
  21개 명시적 표현은 모든 위기 표현을 포괄하지 않는다. 간접 표현과 구어 변형의
  미탐 및 부정·인용의 오탐을 후속 말뭉치에서 별도로 기록해야 한다.

### 검증 근거

- 앱·실제 프록시 함수·실제 대화 엔진 집중 검사 892건 통과. 영어 및 세 추가 언어의
  red 입력을 mock/live 설정에서 실행해 한도 조회·모델 호출·업로드 없이 고정 안내와
  안전 기록 두 건만 남는지 확인했다. 실제 공급자 모델을 호출한 측정은 아니다.
- 대시보드·동의/취소 경계·법무 인용의 관련 1,008건 통과. 테스트 로더는 실제
  import map 또는 실제 모듈을 읽으며 새 판정을 stub으로 대체하지 않는다.
- 공식 배포의 SHA-256을 확인한 Deno 2.9.7에서 `check:edge-runtime`: 16 entrypoints 통과.
- 전체 `npm run verify`: 1,114묶음·18,516건 통과, 1건 건너뜀. 독립 검토는 아직 전이다. 이 문서는
  사람의 번역 검토나 새 법무 승인 기록이 아니며 기존 검토 날짜를 바꾸지 않았다.
