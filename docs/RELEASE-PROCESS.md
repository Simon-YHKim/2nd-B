# 릴리스 · 업데이트 알림 프로세스 (2026-08-09)

> 어떤 릴리스가 사용자를 가로막아도 되는지 정하는 문서. 결론부터: **major 만
> 팝업을 띄운다. minor 와 patch 는 조용히 나간다.**
>
> 공지를 실제로 내보내는 절차(SQL, 예약 게시, 철회)는 `docs/OPERATIONS-NOTICES.md`
> 에 있다. 이 문서는 그 앞 단계 - **띄울지 말지를 판단하는 규칙** - 만 다룬다.

## R0 — 한눈에

| 버전 변화 | 뜻 | 팝업 | 누가 결정하나 |
|---|---|---|---|
| `1.4.2 → 2.0.0` (major) | **쓰던 방법이 바뀐다** | **뜬다** | 사람이 번호를 정하고, 번호가 팝업을 정한다 |
| `1.4.2 → 1.5.0` (minor) | 기능이 늘었다, 기존 동선은 그대로 | 안 뜬다 | 〃 |
| `1.4.2 → 1.4.3` (patch) | 고쳤다 | 안 뜬다 | 〃 |

판단 기준은 규모가 아니라 **재학습**이다. 3주 걸린 기능이라도 어제 쓰던 방법이
오늘도 통하면 major 가 아니고, 버튼 하나를 옮겨도 통하지 않으면 major 다.

```
버전 올리기 → CHANGELOG 항목 정리 → npm run notice:release → (major 면) 사람이 SQL 실행
```

## R1 — 버전 번호가 곧 정책이다

이 저장소의 버전 정본은 **`app.json` 의 `expo.version`** 이다.

- `scripts/check-ota-runtime.js` 가 `npm run verify` 와 EAS Update 직전에 형식을
  검사하는 유일한 버전이다.
- 앱이 실행 중에 읽어올 수 있는 유일한 버전이기도 하다
  (`Constants.expoConfig.version`, `src/lib/notices/version.ts` 의 `getAppVersion()`).
- `notices.min_app_version` 이 비교하는 대상이 바로 이 값이다.
- `package.json` 의 `version` 은 이 파이프라인과 무관하다. OTA 런타임 버전
  (`runtimeVersion`) 도 아니다 - 그쪽은 fingerprint 해시라 버전 비교가 성립하지
  않는다.

**판단은 사람이 번호에 담고, 도구는 번호만 읽는다.** 스크립트가 diff 를 보고
"이건 흐름이 바뀐 것 같은데요" 를 추론하지 않는 이유는, 그 추론이 틀렸을 때
반박할 방법이 없기 때문이다. 대신 아래 R2 · R3 의 질문에 답해서 번호를 정한다.

> ⚠️ **지금 상태 (2026-08-09):** `app.json` = `0.1.0`, `CHANGELOG.md` 의 최신
> 릴리스 섹션 = `0.0.3`. 둘이 벌어져 있다. 다음 릴리스를 자를 때
> `## [Unreleased]` 를 실제 버전 제목으로 바꾸면서 함께 맞춘다 (R5).

## R2 — OTA (EAS Update) 판단 기준

OTA 는 JS 번들만 바꾼다. `app.json` 이 `runtimeVersion.policy = "fingerprint"` 로
고정돼 있어서 **네이티브 입력이 같은 빌드에만** 닿고, 닿는 사람은 앱을 다시 켜는
순간 거의 전원이 새 번들로 옮겨간다.

그래서 OTA 에서 물을 질문은 하나다:

> **어제 하던 조작이 오늘도 통하는가?**

통하면 minor 이하다. 통하지 않으면 major 이고, 팝업 없이 내보내면 사용자는
"버그가 났다" 고 읽는다.

| # | 예시 | 판정 | 왜 |
|---|---|---|---|
| 1 | 리즈닝이 자동 실행에서 **자료를 고른 뒤 실행**하는 방식으로 바뀜 | **major** | 어제 되던 조작이 오늘 없다. 사용자가 방법을 다시 배워야 한다 |
| 2 | 홈에 **공지함 벨**이 새로 생김 | minor | 기존 동선은 그대로고 진입점이 하나 늘었을 뿐이다 |
| 3 | 별 밝기 계산의 반올림 오차 수정 | patch | 화면이 조금 다르게 보이지만 조작은 동일하다 |

**OTA 의 특수 사정:** 옮겨가는 속도가 빨라서 "아직 구버전인 사람" 집단이 거의
생기지 않는다. 그래서 major OTA 의 팝업은 사실상 전원이 **새 기능 안내** 쪽으로
받는다. 업데이트 안내 문구가 실제로 쓰이는 곳은 R3 다.

## R3 — 스토어 릴리스 판단 기준

스토어 릴리스는 바이너리를 새로 올린다. OTA 와 결정적으로 다른 점은 **구버전이
계속 살아 있다** 는 것이다. 업데이트를 미룬 사람, 자동 업데이트를 꺼둔 사람,
심사 대기 중인 플랫폼의 사람이 동시에 존재한다.

그래서 스토어에서는 질문이 하나 더 붙는다:

> **어제 하던 조작이 오늘도 통하는가?**
> **그리고 아직 구버전인 사람이 이 소식을 들어야 하는가?**

| # | 예시 | 판정 | 왜 |
|---|---|---|---|
| 1 | 로그인이 **메일 링크에서 코드 입력**으로 바뀜 | **major** | 재학습이 필요하고, 구버전 사용자는 링크가 안 와서 막힌다 |
| 2 | 무료 등급 주간 한도가 **줄어듦** | **major** | 조작은 그대로지만 사용자가 이미 내린 결정(무료로 계속 쓸지)을 다시 내려야 한다 |
| 3 | Health Connect 연동 추가 (네이티브 권한이라 OTA 로는 못 나감) | minor | 새 기능이지만 기존 사용 흐름은 하나도 바뀌지 않는다 |

세 번째 줄이 경계선이다. **"네이티브 변경이라 스토어로 나간다" 는 것과 "흐름이
바뀐다" 는 것은 다른 이야기**다. 배포 경로가 무거워졌다고 major 가 되지는 않는다.

**스토어의 특수 사정:** 여기서 비로소 청중이 둘로 갈린다. 그래서 major 공지는
`min_app_version` 에 새 버전을 적어 두 집단에 다른 문구를 보낸다 (R6).

## R4 — 1.0.0 이전 (지금 우리)

엄격한 semver 에서 `0.1.0 → 0.2.0` 은 **minor** 다. major 자리가 움직이지 않으므로
1.0.0 을 자르기 전에는 **어떤 릴리스도 자동으로 major 로 분류되지 않는다.**

이건 버그가 아니라 semver 의 정의이고, `src/lib/release/__tests__/semver.test.ts`
에 그대로 박아 뒀다. 지금 시점에 흐름이 바뀌는 릴리스를 내보내려면 둘 중 하나다.

1. **1.0.0 을 자른다.** 출시 릴리스라면 이쪽이 정직하다.
2. 강제하고 **PR 본문에 이유를 쓴다.** 이유를 쓰게 만드는 것이 이 플래그의 존재
   이유다. 판단이 번호와 어긋났다는 사실이 리뷰에 남는다.

   ```bash
   npm run notice:release -- --force-major
   ```

   > ⚠️ **`--` 를 빼면 안 된다.** npm 은 `npm run notice:release --force-major` 의
   > 플래그를 스크립트에 넘기지 않고 자기 설정으로 먹는다. 그러면 스크립트는
   > 플래그를 못 본 채 `SILENT` 를 출력하고, 그게 "공지 필요 없음" 처럼 읽힌다.
   > 스크립트가 이 상황을 감지해서 **에러로 멈추게** 해뒀지만, 애초에 `--` 를 쓴다.
   > (같은 이유로 announce 플래그 이름은 `--version` 이 아니라 `--announce` 다.
   > `--version` 은 npm 이 가로채서 스크립트가 아예 실행되지 않는다.)

## R5 — 릴리스 절차

1. **버전 올리기** - `app.json` 의 `expo.version`. R2 · R3 로 자리수를 정한다.
2. **CHANGELOG 자르기** - `## [Unreleased]` 를 `## [X.Y.Z] - YYYY-MM-DD` 로 바꾸고
   그 위에 빈 `## [Unreleased]` 를 새로 연다.
3. **`npm run verify`** - `check:ota-runtime` 이 버전 형식과 fingerprint 정책을 본다.
4. **`npm run notice:release`**
   - minor · patch 면 `SILENT` 를 출력하고 끝난다. **할 일 없음.**
   - major 면 INSERT 문을 출력하고 멈춘다.
5. **(major 만) 사람이 발행** - 출력된 SQL 을 **그대로 붙여넣지 말고**:
   - `title_ko` · `body_ko` 를 한국어로 다시 쓴다. 스크립트는 번역하지 않으므로
     초안에는 영어가 양쪽에 들어 있다.
   - 사용자 언어로 다시 쓴다. CHANGELOG 는 코드를 설명하고, 공지는 **사용자가
     이제 무엇을 할 수 있는지**를 설명한다.
   - 임상 용어를 쓰지 않는다 (`src/lib/safety/lexicon.ts` 가 정본이다. 공지 본문은
     DB 로 들어가므로 CI 스캔이 닿지 않는다).
   - Supabase SQL Editor 에 붙여넣고 실행한다. 앞에 붙은 조회문으로 이 버전에
     이미 올라간 공지가 있는지 먼저 본다.

   INSERT 는 **두 번 실행해도 한 건만** 들어간다. 단 **철회된**
   (`withdrawn_at`) 공지는 막지 않으므로, 잘못 쓴 공지를 내리고 고쳐서 다시
   올리는 게 그대로 된다 (`docs/OPERATIONS-NOTICES.md` N5).

**CI 는 이 스크립트를 실행하지 않는다.** `npm run verify` 체인에 없고, 스크립트
자체가 `process.env.CI` 를 보고 거절한다. 그리고 `src/lib/release/` 와
`scripts/release-notice.ts` 어디에도 Supabase import 가 없다 - 공지를 자동 발행할
수 있는 경로가 애초에 존재하지 않는다는 뜻이고, 그게 이 설계의 요점이다.

## R6 — 앱이 보여주는 것

major 공지는 `min_app_version` 에 **자기가 알리는 버전**을 담고 나간다. 앱은 그
숫자를 실행 중인 버전과 비교해 문구를 가른다 (`src/lib/release/update-notice.ts`).

| 실행 중인 버전 | 보이는 것 | 버튼 |
|---|---|---|
| `>= min_app_version` | **새 기능 안내** - 본문 그대로 | 확인 |
| `< min_app_version` | 본문 + **"X.Y.Z 버전부터 쓸 수 있어요"** 한 줄 | 네이티브: 업데이트(스토어) · 웹: 새로고침 |

두 집단 **모두** 팝업을 본다. 이건 `min_app_version` 의 원래 용법과 다르므로
`src/lib/notices/select.ts` 에서 kind 로 갈라 뒀다.

- **major** - 버전은 숨김 조건이 아니라 **어느 릴리스 이야기인지**를 적어둔 값이다.
  구버전 사용자야말로 아직 행동할 게 남은 사람이므로 숨기지 않는다.
- **minor** - 기존대로 **숨김 조건**이다. 없는 버튼 이야기는 혼란만 준다
  (`docs/OPERATIONS-NOTICES.md` N4).

불확실하면 전부 **새 기능 안내** 쪽으로 실패한다. 버전을 못 읽거나 값이 깨졌을 때,
멀쩡한 사용자에게 "앱이 낡았다" 고 말해 아무것도 없는 스토어 페이지로 보내는 쪽이
더 나쁘기 때문이다.

## R7 — 하면 안 되는 것

- **CI 에서 공지를 INSERT 하지 않는다.** `notice:release` 를 `verify` 에 넣지 않는다.
  발행은 사람이 한다.
- **팝업을 아껴 쓴다.** 안 봐도 되는 공지가 반복되면 사용자는 읽지 않고 닫는 법을
  배우고, 그러면 정작 필요한 장애 공지가 안 닿는다. 미읽은 major 가 여러 건이어도
  한 번에 한 건만 뜬다 (한 화면 한 메시지).
- **흐름이 바뀌는데 minor 로 올리지 않는다.** 팝업을 피하려고 번호를 낮추면 정책이
  아니라 습관이 된다. 번호가 곧 약속이다.
- **`min_app_version` 을 보안 경계로 쓰지 않는다.** 클라이언트가 거는 UX 필터이고
  실패하면 열리는 쪽이다. 숨겨야 하는 내용은 애초에 공지에 쓰지 않는다.
- **버전을 세 군데에 손으로 적지 않는다.** 정본은 `app.json` 하나다.
