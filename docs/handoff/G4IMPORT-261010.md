## 기존 데이터와 취소 원장

- 기존 활성 행의 `profile_before`/`profile_patch`와 선행 ID로 필드 원장을 backfill한다.
- 앞선 취소의 undo는 활성 후속 batch에서 도달할 수 있는 동안만 남긴다. 마지막 의존 batch 취소 후 지운다. 콘텐츠 전체 삭제 뒤에는 개인 내용이 남은 undo가 없어야 한다.
- 0239가 이미 지운 취소 행의 before/after는 복원할 수 없다. 새 값을 추측하지 않는다. 그런 선행 행이 기록된 활성 batch는 해당 이전 값의 복원 가능성을 보수적으로 `before_known=false`로 둔다. 값이 남아 있다면 사용자의 수동 편집이 필요하다.
- 과거 수동 편집의 작성 이력은 0239에 없다. backfill은 남아 있는 값과 선행 원장을 이용할 뿐 과거 사건을 완전히 재구성하지 못한다. 새 수동 저장부터 필드 연결 해제가 적용된다.
- 새 테이블·상태·작업 큐는 없다. 추가 칸은 `profile_context_imports.field_undo`, `users.profile_import_attempt_day`, `users.profile_import_attempt_count` 세 개다. 0240의 retained 등록과 owner FK cascade를 그대로 쓰며, 칸별 삭제 정책은 `db/migration-drafts/service-contract-erasure-entries.json`의 `columnPolicies`와 SQL COMMENT에 적었다. 기존 registry-only 마이그레이션은 재생 가능하게 그대로 둔다.

## 한도와 Simon 결정 필요

0242 `apply_profile_context_import`의 이름 붙은 상수 세 개가 변경 지점이다.

| 상수 | 잠정값 | 집계 |
|---|---:|---|
| `daily_attempt_limit` | 10 | UTC 날짜 기준. 새 요청의 성공·확인 누락·입력 오류·CAS 충돌·용량 거절 포함. 동일 영수증 재전송 제외. |
| `active_batch_limit` | 20 | `status='active'` 행 수. |
| `retained_byte_limit` | 2,097,152 (2 MiB) | 모든 행의 document UTF-8 JSON 바이트 + field_undo JSON 바이트 + 행마다 영수증 비용 512바이트. 취소 영수증도 포함하여 취소 반복으로 무한히 쌓이지 않게 한다. |

사용자가 제공한 기존 행 수는 4다. DB에 접속하지 않고 최악 `4 × 256 KiB = 1 MiB`로 계산했다.
1 MiB는 문서만으로 꽉 차며 undo/영수증 여유가 없다. 따라서 지시한 대안 2 MiB를 택했다.
7개 제한된 프로필 필드의 before/after와 ID 메타데이터를 포함한 네 원장의 추가분은 1 MiB보다 작다.
따라서 제공된 4행 조건은 새 집계 상한 아래다. 실제 document 크기·상태·내용은 조회하지 않았다.

이 값은 **논리 보관량**이다. source/page는 같은 문서의 고정 렌더링 사본이고, DB 행·인덱스·TOAST 등 실제 디스크 크기를 2 MiB로 제한한다는 뜻은 아니다.
실제 저장 공간 기반으로 바꾸려면 집계식과 한도값을 함께 결정해야 한다. 값을 바꾸면 SQL 병렬 경계 테스트의 대응 상수도 갱신한다.

입력 실패 때 SQL 예외를 RPC 밖으로 던지면 횟수 증가도 롤백된다. 그래서 예상 가능한 입력/CAS/한도 실패는 내부 subtransaction에서 잡고 기존 `{code,message,details,hint}` 모양과 HTTP 400/403/409/429를 반환한다. 알 수 없는 DB 오류는 그대로 롤백한다.
[PostgREST 트랜잭션·response.status 계약](https://docs.postgrest.org/en/stable/references/transactions.html)에 따른다. 로컬 SQL에서 코드·설정·잔존 카운터를 확인했고, 실제 운영 HTTP 호출은 하지 않았다.

결정할 항목:

1. 하루 10회, 활성 20개, 논리 2 MiB를 승인하거나 상수·집계 방식을 변경한다.
2. 모든 항목의 개별 확인을 유지할지 판단한다. 가장 작은 안전 변경은 기존 확인 기능의 공통 적용이다. 일괄 확인을 새로 도입하거나 외부 출처를 검증하는 별도 UX는 만들지 않았다. 모두 선택은 확인한 항목을 고르는 기능으로 유지한다.
3. G4-05 계정 export의 batch 포함 범위(원문·확인·상태와 내부 digest/undo 공개 여부) 및 최소 service 읽기 권한을 별도 결정한다.
