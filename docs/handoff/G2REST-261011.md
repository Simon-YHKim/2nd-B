## 재현과 변경

### G2-05

0236은 cron 스키마가 없으면 예약 없이 성공한다. GitHub workflow와 runner는
`DASHBOARD_RETENTION_ENABLED`가 true가 아니면 purge를 건너뛴다. configure와 DB guard는
최근 purge 성공 여부를 보지 않는다. 현재 코드에서 성립한다.

- 기존 저장소를 먼저 확인했다. `dashboard_generation_settings`는 사용자별 timezone/locale이고,
  `polaris_generation_config`는 별도 기능 전용이다. 재사용할 공용 dashboard 설정은 없다.
  0245의 `dashboard_generation_retention` 한 행에 `last_purged_at`만 저장한다.
  사용자 식별자·생성문이 없어 소유자 표를 분류하는 erasure registry의 대상이 아니다.
  0237의 기존 두 행·FK cascade는 유지하고 새 등록부 행은 만들지 않는다.
- `dashboard_generation_retention_ready()`에 잠정 허용 시간 `retention_max_age`를 한 곳에 둔다.
  없는 행, 미래 시각, 3시간 이상 지난 성공 시각은 false다. DB 시계 `clock_timestamp()`를 쓴다.
- `dashboard_generation_guard()`가 이 함수를 검사한다. 기존 request·cache·dispatch·audit_attempt·finish는
  그대로 guard를 사용하므로 옛 Edge도 새 DB에서 같은 조건을 따른다. G2-06의 v2 경로에도 같은 guard를 적용한다.
- purge의 기존 만료 출력 제거·48시간 시도 행 정리를 유지하고 같은 트랜잭션 마지막에 heartbeat를 갱신한다.
  중간 실패는 전체 rollback이므로 성공 표식이 남지 않는다. 0245 자체가 이 purge를 한 번 실행해
  실제 정리 성공으로 초기값을 심는다. cron이 없는 환경에서도 적용 직후 동작한다.
- 운영 pg_cron이 이미 부르는 `purge_dashboard_generation()`의 signature는 같다.
  GitHub도 같은 RPC를 부르며 이제 retention 변수와 무관하게 실행한다. 생성 OFF·cron secret 부재에서도 purge는 먼저 돈다.
- configure는 ON으로 쓸 때 DB readiness가 정확히 true인지 확인한다. 조회 오류·빈/잘못된 응답은 거절한다.
  OFF는 보관 상태나 모델 가용성에 의존하지 않는다. Variables·시크릿은 변경하지 않았다.
- 새 표는 RLS/FORCE RLS, 직접 DML/SELECT 권한 없음. 함수는 SECURITY DEFINER·빈 search_path·
  명시적 REVOKE를 사용한다. 파일 끝 GRANT는 readiness와 purge의 service_role EXECUTE뿐이다.

heartbeat는 정리가 중단된 동안 새 생성을 차단한다. 중단된 작업을 자동 복구하거나
이미 남은 행을 스스로 지우는 장치는 아니다. 오래된 행의 실제 제거는 purge 복구가 필요하다.

### G2-06

0238의 같은 키 분기는 실패·낡은 pending에서 항상 waiting이다. provider가 tier/capacity RPC 전에
끝나도 handler의 finish(null)이 failed로 바꾸고 다음 요청을 막는다. 코드와 로컬 SQL로 확인했다.

- 기존 0245 안에 `lease_token`, `leased_at`, `dispatched_at` 세 열과 v2 RPC 네 개를 추가했다.
  새 표·큐·화면·응답 kind 변경은 없다. `created_at`과 같은 키의 run 행을 보존한다.
  2회차에서 quota를 첫 예약과 재예약 각각의 시도 수로 보강했다(아래 절).
- claim은 사용자 잠금과 run 행 잠금 아래 lease를 발급하고 감사 시도 행도 같은 트랜잭션으로 만든다.
  재예약은 명시적 호출 전 실패 또는 3분 이상 지난 pending이면서 `dispatched_at IS NULL`인 경우뿐이다.
  이전 lease의 +attempt를 +pre_dispatch_failed로 닫고 새 token을 만든다. 모호하면 재예약하지 않는다.
- 실행 단위는 lease다. `ai_audit_log.id=lease_token`, `outbox_event_id=dashboard:<run id>:<lease token>`으로
  같은 키 아래 각 실행의 계보를 보존한다. claim 직후 중단도 감사 1행이 있으며, dispatch 직전에 같은 행에
  실제 model·effort·prompt hash를 쓰고 dispatch 표시를 원자적으로 남긴다. 결과는 그 행만 갱신한다.
  이전 lease의 감사 행을 지우거나 새 시도로 덮지 않는다. 실제 model을 아직 정하지 못한 시도는
  `dashboard+attempt`이고 호출 전에 끝나면 `dashboard+pre_dispatch_failed`다. 실제 모델을 호출한 이력이 아니다.
  결과 값은 기존 model_used 접미사 관례를 따르며, 호출 전 실패는 내부 종료 경로가 기록하므로
  0244 result RPC의 외부 입력 허용목록을 넓힐 필요가 없다.
- provider의 dispatch 직전 RPC, handler의 finish, provider의 audit_result 모두 claim token을 보낸다.
  DB가 현재 token과 비교하므로 이전 실행은 재예약 뒤 호출·저장·감사 결과 갱신을 할 수 없다.
  dispatch 표시 뒤에는 응답 유실·timeout·HTTP 실패·동의 철회와 관계없이 그 키를 다시 예약하지 않는다.
- red로 끝내는 경로는 heartbeat나 lease 시간 만료에 의존하지 않는다. service_role 확인과
  사용자/run 잠금·현재 token 검사는 유지하므로 재예약된 옛 실행은 여전히 거절된다.
  실제 유료 dispatch만 heartbeat·lease 시간·현재 동의·소스가 모두 유효해야 한다.
- 옛 RPC 이름과 인자는 유지한다. 옛 Edge가 만든 NULL lease 행은 원래 흐름대로 동작한다.
  기존 행과 옛 Edge의 새 행은 dispatch 여부가 불명확하므로 보수적인 표시 기본값을 둔다.
  v2가 그 행을 재예약하지 않는다. 옛 dispatch/finish/audit_attempt는 v2 lease 행을 바꿀 수 없다.
- 0236/0237/0238/0244는 수정하지 않았다. 기존 run owner/cascade와 감사 삭제 규율을 그대로 사용하므로
  삭제 등록부를 늘리지 않는다. v2 네 함수도 definer/search_path·service_role 전용 GRANT를 지킨다.

## 2회차: 재예약 한도와 heartbeat 복구 경합 (G2-06)

원문: `E:/Coding Infra/reports/qa-legacy-261004/gates/n7-g2rest-daybreak-r1.txt`.
판정은 BLOCK, 신규 medium 2건이다. 이 회차는 그 두 건만 수정하며 G2-05·G2-07의
폐쇄 판정, 3시간 잠정값, 어휘 정책은 유지한다. 아래의 이전 회차 daybreak 결과와 구분한다.

### 발견 1: 한도는 예약된 키가 아니라 그날의 시도 수

- 최초 예약과 재예약을 각각 1회로 센다. `daily_note` 3회, `day_summary`·`inbox_triage` 48회다.
  사용자 현재 시간대의 로컬 날짜 **또는** UTC 날짜가 같으면 합산하는 기존 규칙을 유지한다.
  같은 시도가 양쪽 날짜에 속해도 한 번만 센다. 로컬 자정이나 UTC 자정 한쪽만 넘겨서는 열리지 않는다.
- `dashboard_generation_attempt_count`가 v2의 `server_verified` 감사 행을 lease별 `created_at`으로 센다.
  정확한 `dashboard:<run UUID>:<audit UUID>` 계보를 확인한다. 옛 Edge의 NULL lease run은 1회로 합산해
  기존 감사 행과 이중 계산하지 않는다. 두 request RPC가 같은 내부 함수를 사용한다.
- 사용자 잠금 아래 한도를 검사한 뒤에만 lease 교체와 감사 INSERT를 한다.
  `pre_dispatch_failed`와 3분 지난 미dispatch pending 모두 해당한다.
  한도에 닿으면 `limited`이고 기존 lease·감사 행·감사 결과는 그대로다.
- 리뷰에서 발견한 같은 결함의 경계도 닫았다. +14에서 -12로 이동하면 triage 날짜 키가
  50시간 이어질 수 있다. 최초 run의 48시간 purge가 최근 lease의 일일 한도를 없애지 않도록
  감사 행을 run과 독립적으로 센다. 새 표·카운터 열·보관 기간 변경은 없다.

### 발견 2: 적격성과 retention 분리

- 내부 `dashboard_generation_eligibility(uuid)`에 역할 확인, 계정 상태, 성인, 추천 동의,
  현재 consent snapshot 검사를 모았다. 잠금 순서는 0194와 같은 삭제 advisory → auth → users다.
  이 함수와 한도 helper의 EXECUTE는 PUBLIC·anon·authenticated·service_role 모두 회수했다.
- 기존 `dashboard_generation_guard(uuid)`는 같은 적격성 함수 + 잠금 후 retention 검사다.
  시그니처와 옛 Edge의 허용·거절 응답은 그대로다. 잠금을 기다리는 동안 heartbeat가 낡아진 경우도 닫힌다.
- `finish_v2(NULL)`는 사용자/run 잠금 아래 적격성과 run의 consent token 일치를 판정한다.
  미dispatch pending이 적격이면 heartbeat와 무관하게 `pre_dispatch_failed`다.
  철회·정지·미성년·현재 token 불일치 등은 `failed`, 기존 failed·red blocked는 종결 상태를 유지한다.
  dispatch 이후 출력 저장에는 여전히 retention을 요구한다.
- 같은 눈으로 본 결과: `request_v2`와 `audit_attempt_v2`에는 잠금 전 heartbeat를 읽는 공통 guard가
  있었으므로 위 순서 변경이 함께 적용된다. 둘에는 finish처럼 원인을 역으로 추정하는 분기는 없었다.
  red 종료는 기존대로 heartbeat·lease 나이와 무관하다. `audit_result_v2`에는 혼용이 없다.
  guard·heartbeat를 읽지 않고 advisory → users → run → audit 잠금 뒤 현재 lease/dispatch만 확인하며,
  철회 후에도 결과 증거를 남기는 #2223 규칙을 유지한다.

### 2회차 검증

- 로컬 PostgreSQL 18: 3개 purpose × 호출 전 실패/만료 pending/정상 완료 **9개 한도 시나리오**.
  N회 성공, N+1 limited, lease·감사 불변, 새 키와 옛 Edge의 한도 공유, run purge 뒤 한도 유지를 확인했다.
  로컬 전용·UTC 전용 날짜, 최초 run 날짜와 최근 시도 날짜 분리, 다음 날짜의 새 한도도 통과했다.
- 서로 다른 두 키가 마지막 1회를 두고 경합하면 claimed 1 + limited 1, 감사는 총 3행이다.
- 실제 3세션 경합은 A의 users 잠금, B의 Lock 대기와 blocking PID, C의 purge 완료를 순서대로 확인한 뒤
  A를 해제한다. 적격 finish는 복구하고 철회·token 불일치는 종결하는 **3/3**,
  request/dispatch가 대기 중 낡아진 heartbeat를 거절하는 **2/2**를 통과했다.
- 8개 적격성 거절 대조, 기존 이중 dispatch 금지·옛 lease 차단·red 종결·감사 원자성·ACL,
  실제 consent 함수의 철회/finish 경합 **8개**, writer/audit-result 경합 **4개**를 다시 통과했다.
- 첫 한도 회귀는 기존 코드에서 네 번째 `claimed`를 반환해 실패했다. 첫 전체 SQL 재실행 2회는
  fixture의 반복 timezone 목록 조회로 60초 제한에 닿았다. 첫 설정 후 저장된 timezone을 재사용하도록
  테스트를 고친 뒤 전체 SQL이 통과했다. 이 두 실행은 성공 수에 넣지 않는다.

### 발견 1: 최근에 재예약한 실행을 purge가 지움

purge의 삭제 조건을 `created_at < now()-48h AND (lease_token IS NULL OR leased_at < now()-48h)`로 바꿨다.
legacy는 기존 기준을 유지하고, v2는 마지막 예약부터도 최소 48시간 남는다. lease 열 추가를
purge 정의·초기 호출보다 앞으로 옮겼으므로 0244까지만 적용된 스키마에서도 그대로 실행된다.
만료 출력 제거와 성공 heartbeat 갱신은 기존과 같다. 감사는 purge 대상이 아니며 기존 독립 보관 규율을 따른다.

재예약이 먼저 잠그면 DELETE가 갱신된 lease를 다시 확인하고 보존한다. purge가 먼저 삭제하면
재요청이 새 run을 잡고, 이전 감사는 남는다. 양쪽 순서에서 현재 lease 하나만 남고, 그 lease가
dispatch된 뒤의 purge·재요청으로 두 번째 호출 권한이 생기지 않는 것을 실제 두 연결로 검사했다.
일일 한도는 기존처럼 lease별 감사 시각의 로컬 날짜 OR UTC 날짜로 센다. 보관 변경으로 계수를 줄이지 않는다.

### 발견 2: red 감사 실패를 일반 실패로 처리함

- provider가 red 판정 직후 `onBlocked('red')`로 handler 내부 상태를 고정한다.
  `attempt(true)`의 error·false·throw와 무관하게 handler는 일반 `finish_v2(NULL)`를 호출하지 않는다.
- 새 `dashboard_generation_block_v2`가 현재 미dispatch lease의 감사 1행을 `+crisis`, `safety_zone=red`로
  갱신하고 run을 `pre_dispatch_blocked`로 원자 종결한다. 이미 같은 결과이면 반복 호출해도 같은 증거다.
  heartbeat·lease 3분 경과에 의존하지 않는다. 옛 token·dispatch 표시가 있으면 아무것도 바꾸지 않는다.
  철회가 먼저 `failed`로 만든 경우에는 그 상태를 유지하며 red 감사만 닫을 수 있다.
- **DB가 계속 불가한 경우의 선택**: terminal 재시도만으로는 3분 pending 복구를 막을 수 없다.
  따라서 판정 전에 새 `dashboard_generation_begin_classification_v2`가 기존 감사 placeholder를
  `dashboard+attempt`에서 `dashboard+classifying`으로 바꾸고, ACK=true인 실행만 판정한다.
  새 표·열·큐·외부 응답 kind는 없다. 이미 시작한 판정에는 다시 ACK를 주지 않는다.
- stale pending의 자동 복구는 아직 `dashboard+attempt`인 경우만 허용한다.
  terminal RPC가 계속 실패하면 `pending/+classifying`을 유지하고 같은 키는 waiting이다.
  실제 red 결과가 DB에 확정됐다고 허위 기록하지 않는다. 모델 fetch는 0이고 감사 행 수도 1이다.
  해당 키는 그날/슬롯에 멈출 수 있으며 기존 48시간 보관·purge를 따른다. 자동 보정·재시도 큐는 없다.

  claim 직후 중단은 `+attempt`로 남으므로 기존 3분 복구가 가능하다.
- green 판정 뒤 호출 전 오류는 기존 finish가 `+classifying`도 `+pre_dispatch_failed`로 닫아 재예약할 수 있다.

```sql
    ON a.user_id=g.user_id AND a.purpose=g.purpose AND a.event_source='server_verified'
    AND a.outbox_event_id='dashboard:'||g.id||':'||a.id
  WHERE g.lease_token IS NOT NULL GROUP BY g.id
)
SELECT lease_attempts,distinct_leases,count(*) AS runs FROM lineage
GROUP BY lease_attempts,distinct_leases ORDER BY lease_attempts;
-- run 보관 기한 뒤에도 최근 시도의 감사와 일일 quota는 남는다.
SELECT count(*) AS recent_leases_after_run_purge FROM public.ai_audit_log a
WHERE a.event_source='server_verified' AND a.created_at>=now()-interval '24 hours'
  AND a.outbox_event_id ~ ('^dashboard:[0-9a-f]{8}(-[0-9a-f]{4}){3}-[0-9a-f]{12}:'||a.id::text||'$')
  AND NOT EXISTS(SELECT 1 FROM public.dashboard_generation_runs g
    WHERE g.id::text=split_part(a.outbox_event_id,':',2));
```

guard·eligibility·attempt_count는 세 역할 모두 false, readiness/purge/v2 RPC는 service_role만 true여야 한다.
새 표는 세 역할에 직접 읽기/쓰기 권한이 없어야 한다. 0237의 두 행은 account_delete_only 그대로다.
