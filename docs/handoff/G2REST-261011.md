## 재현과 변경

### G2-05

0236은 cron 스키마가 없으면 예약 없이 성공한다. GitHub workflow와 runner는
`DASHBOARD_RETENTION_ENABLED`가 true가 아니면 purge를 건너뛴다. configure와 DB guard는
최근 purge 성공 여부를 보지 않는다. 현재 코드에서 성립한다.

- 기존 저장소를 먼저 확인했다. `dashboard_generation_settings`는 사용자별 timezone/locale이고,
  `polaris_generation_config`는 별도 기능 전용이다. 재사용할 공용 dashboard 설정은 없다.
  0245의 `dashboard_generation_retention` 한 행에 `last_purged_at`만 저장한다.
  사용자 식별자·생성문이 없어 소유자 표를 분류하는 erasure registry의 대상이 아니다.
  0237의 기존 두 행·FK cascade는 유지하고 새 등록부 행은 만들지 않는다.
- `dashboard_generation_retention_ready()`에 잠정 허용 시간 `retention_max_age`를 한 곳에 둔다.
  없는 행, 미래 시각, 3시간 이상 지난 성공 시각은 false다. DB 시계 `clock_timestamp()`를 쓴다.
- `dashboard_generation_guard()`가 이 함수를 검사한다. 기존 request·cache·dispatch·audit_attempt·finish는
  그대로 guard를 사용하므로 옛 Edge도 새 DB에서 같은 조건을 따른다. claim/terminal 함수는 수정하지 않았다.
- purge의 기존 만료 출력 제거·48시간 시도 행 정리를 유지하고 같은 트랜잭션 마지막에 heartbeat를 갱신한다.
  중간 실패는 전체 rollback이므로 성공 표식이 남지 않는다. 0245 자체가 이 purge를 한 번 실행해
  실제 정리 성공으로 초기값을 심는다. cron이 없는 환경에서도 적용 직후 동작한다.
- 운영 pg_cron이 이미 부르는 `purge_dashboard_generation()`의 signature는 같다.
  GitHub도 같은 RPC를 부르며 이제 retention 변수와 무관하게 실행한다. 생성 OFF·cron secret 부재에서도 purge는 먼저 돈다.
- configure는 ON으로 쓸 때 DB readiness가 정확히 true인지 확인한다. 조회 오류·빈/잘못된 응답은 거절한다.
  OFF는 보관 상태나 모델 가용성에 의존하지 않는다. Variables·시크릿은 변경하지 않았다.
- 새 표는 RLS/FORCE RLS, 직접 DML/SELECT 권한 없음. 함수는 SECURITY DEFINER·빈 search_path·
  명시적 REVOKE를 사용한다. 파일 끝 GRANT는 readiness와 purge의 service_role EXECUTE뿐이다.

heartbeat는 정리가 중단된 동안 새 생성을 차단한다. 중단된 작업을 자동 복구하거나
이미 남은 행을 스스로 지우는 장치는 아니다. 오래된 행의 실제 제거는 purge 복구가 필요하다.

고정 enum·내부 경로·ID·ISO 날짜는 자유문이 아니며 기존 스키마 제약을 유지한다.

  거절된 결과는 0244가 이미 받는 `rejected_output`으로 감사한다. 원문은 감사에 싣지 않는다.
  handler는 기존 `finish(null)`과 고정 `unavailable`로 끝낸다. schema/근거 거절도 같은 결과로 기록된다.

  오래된 금지 출력도 다시 표시하지 않는다. 기존 DB 행을 새 어휘 검사로 일괄 backfill하지는 않는다.

## 운영 순서 점검표 (이번 세션 실행하지 않음)

   백업, `_sync` 적용 중 표시를 확인한다. 0236/0237/0238/0244가 적용돼 있어야 한다.
   사용자 제공 운영 사실(pg_cron `17 * * * *` active)은 이번 세션에서 원격 재조회하지 않았다.

2. **0245 적용**: 전체 파일을 하나의 migration transaction으로 적용한다.
   마지막 purge가 실패하면 migration 전체를 되돌리고 기존 운영 코드를 유지한다.
   성공하면 heartbeat가 즉시 신선하므로 W1 활성 스위치를 바꾸지 않고 기존 Edge를 계속 쓸 수 있다.
3. **머지**: DB 객체·ACL·heartbeat를 확인한 뒤 별도 담당자가 머지한다.
   새 GitHub workflow는 generation OFF와 무관하게 purge한다. 이전 workflow가 잠깐 남아도
   기존 pg_cron의 같은 purge 함수가 heartbeat를 갱신한다.
4. **dashboard-generate 배포**: Simon GO 뒤에만 기존 schema gate를 거쳐 배포한다.
   이번 Edge는 0245의 새 객체를 직접 호출하지 않는다. 기존 RPC 안의 guard가 DB에서 검사한다.
   따라서 deploy schema inventory에 새 Edge RPC는 없으며, **0245 선적용은 이 머지 조건으로 강제**한다.
   configure의 ON 경로는 새 readiness 객체가 없으면 실패한다. 새 Edge+새 DB는 같은 RPC signature로 동작한다.
5. **확인 조회**: 아래 비내용 집계·ACL·freshness를 확인한다. 다음 매시 17분 purge 후 heartbeat 증가를 확인한다.
   별도 승인된 QA에서 평범한 출력의 ready·감사 completed와 금지 출력의 rejected_output·output 없음,
   오래된 heartbeat에서 dispatch 없음, generation OFF에서도 purge 성공을 확인한다.
   이번 mock/로컬 SQL 결과를 운영 관측이라고 쓰지 않는다.
6. **되돌림**: 우선 forward repair. Edge 문제가 있으면 이전 reviewed Edge SHA를 재배포하고
   `db/migrations/rollback/0245_down.sql`을 Simon GO로 실행한다. DB guard·표·purge와
   무조건 실행하는 hourly는 유지한다. heartbeat를 가짜 시각으로 갱신하거나 gate를 제거하지 않는다.
   Edge rollback은 새 출력 어휘 차단을 잃으므로 수정 완료 상태가 아니다.

```sql
-- 사전: 생성문·사용자 식별자·자격증명은 출력하지 않는다.
SELECT jobname,schedule,active FROM cron.job WHERE jobname='purge-dashboard-generation';
SELECT status,count(*) FROM public.dashboard_generation_runs GROUP BY status;
-- 0245 적용 뒤:
SELECT last_purged_at,clock_timestamp()-last_purged_at AS age,
  public.dashboard_generation_retention_ready() AS ready
FROM public.dashboard_generation_retention;
SELECT count(*) AS expired_outputs FROM public.dashboard_generation_runs
WHERE expires_at<=now() AND output IS NOT NULL;
SELECT count(*) AS old_attempts FROM public.dashboard_generation_runs
WHERE created_at<now()-interval '48 hours';
SELECT p.proname,p.prosecdef,p.proconfig,
  has_function_privilege('anon',p.oid,'EXECUTE') AS anon_execute,
  has_function_privilege('authenticated',p.oid,'EXECUTE') AS client_execute,
  has_function_privilege('service_role',p.oid,'EXECUTE') AS server_execute
FROM pg_proc p JOIN pg_namespace n ON n.oid=p.pronamespace
WHERE n.nspname='public' AND p.proname IN
  ('dashboard_generation_retention_ready','purge_dashboard_generation','dashboard_generation_guard');
SELECT table_name,class FROM public.erasure_registry
WHERE table_name IN ('dashboard_generation_runs','dashboard_generation_settings');
```
