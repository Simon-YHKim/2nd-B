## 재현과 변경

### G2-05

0236은 cron 스키마가 없으면 예약 없이 성공한다. GitHub workflow와 runner는
`DASHBOARD_RETENTION_ENABLED`가 true가 아니면 purge를 건너뛴다. configure와 DB guard는
최근 purge 성공 여부를 보지 않는다. 현재 코드에서 성립한다.

- 기존 저장소를 먼저 확인했다. `dashboard_generation_settings`는 사용자별 timezone/locale이고,
  `polaris_generation_config`는 별도 기능 전용이다. 재사용할 공용 dashboard 설정은 없다.
  0245의 `dashboard_generation_retention` 한 행에 `last_purged_at`만 저장한다.
  사용자 식별자·생성문이 없어 소유자 표를 분류하는 erasure registry의 대상이 아니다.
  0237의 기존 두 행·FK cascade는 유지하고 새 등록부 행은 만들지 않는다.
- `dashboard_generation_retention_ready()`에 잠정 허용 시간 `retention_max_age`를 한 곳에 둔다.
  없는 행, 미래 시각, 3시간 이상 지난 성공 시각은 false다. DB 시계 `clock_timestamp()`를 쓴다.
- `dashboard_generation_guard()`가 이 함수를 검사한다. 기존 request·cache·dispatch·audit_attempt·finish는
  그대로 guard를 사용하므로 옛 Edge도 새 DB에서 같은 조건을 따른다. G2-06의 v2 경로에도 같은 guard를 적용한다.
- purge의 기존 만료 출력 제거·48시간 시도 행 정리를 유지하고 같은 트랜잭션 마지막에 heartbeat를 갱신한다.
  중간 실패는 전체 rollback이므로 성공 표식이 남지 않는다. 0245 자체가 이 purge를 한 번 실행해
  실제 정리 성공으로 초기값을 심는다. cron이 없는 환경에서도 적용 직후 동작한다.
- 운영 pg_cron이 이미 부르는 `purge_dashboard_generation()`의 signature는 같다.
  GitHub도 같은 RPC를 부르며 이제 retention 변수와 무관하게 실행한다. 생성 OFF·cron secret 부재에서도 purge는 먼저 돈다.
- configure는 ON으로 쓸 때 DB readiness가 정확히 true인지 확인한다. 조회 오류·빈/잘못된 응답은 거절한다.
  OFF는 보관 상태나 모델 가용성에 의존하지 않는다. Variables·시크릿은 변경하지 않았다.
- 새 표는 RLS/FORCE RLS, 직접 DML/SELECT 권한 없음. 함수는 SECURITY DEFINER·빈 search_path·
  명시적 REVOKE를 사용한다. 파일 끝 GRANT는 readiness와 purge의 service_role EXECUTE뿐이다.

heartbeat는 정리가 중단된 동안 새 생성을 차단한다. 중단된 작업을 자동 복구하거나
이미 남은 행을 스스로 지우는 장치는 아니다. 오래된 행의 실제 제거는 purge 복구가 필요하다.

### G2-06

0238의 같은 키 분기는 실패·낡은 pending에서 항상 waiting이다. provider가 tier/capacity RPC 전에
끝나도 handler의 finish(null)이 failed로 바꾸고 다음 요청을 막는다. 코드와 로컬 SQL로 확인했다.

- 기존 0245 안에 `lease_token`, `leased_at`, `dispatched_at` 세 열과 v2 RPC 네 개를 추가했다.
  새 표·큐·화면·응답 kind 변경은 없다. `created_at`과 같은 키의 run 행을 보존하므로 일일 quota가 초기화되지 않는다.
- claim은 사용자 잠금과 run 행 잠금 아래 lease를 발급하고 감사 시도 행도 같은 트랜잭션으로 만든다.
  재예약은 명시적 호출 전 실패 또는 3분 이상 지난 pending이면서 `dispatched_at IS NULL`인 경우뿐이다.
  이전 lease의 +attempt를 +pre_dispatch_failed로 닫고 새 token을 만든다. 모호하면 재예약하지 않는다.
- 실행 단위는 lease다. `ai_audit_log.id=lease_token`, `outbox_event_id=dashboard:<run id>:<lease token>`으로
  같은 키 아래 각 실행의 계보를 보존한다. claim 직후 중단도 감사 1행이 있으며, dispatch 직전에 같은 행에
  실제 model·effort·prompt hash를 쓰고 dispatch 표시를 원자적으로 남긴다. 결과는 그 행만 갱신한다.
  이전 lease의 감사 행을 지우거나 새 시도로 덮지 않는다. 실제 model을 아직 정하지 못한 시도는
  `dashboard+attempt`이고 호출 전에 끝나면 `dashboard+pre_dispatch_failed`다. 실제 모델을 호출한 이력이 아니다.
  결과 값은 기존 model_used 접미사 관례를 따르며, 호출 전 실패는 내부 종료 경로가 기록하므로
  0244 result RPC의 외부 입력 허용목록을 넓힐 필요가 없다.
- provider의 dispatch 직전 RPC, handler의 finish, provider의 audit_result 모두 claim token을 보낸다.
  DB가 현재 token과 비교하므로 이전 실행은 재예약 뒤 호출·저장·감사 결과 갱신을 할 수 없다.
  dispatch 표시 뒤에는 응답 유실·timeout·HTTP 실패·동의 철회와 관계없이 그 키를 다시 예약하지 않는다.
- red로 끝내는 경로는 heartbeat나 lease 시간 만료에 의존하지 않는다. service_role 확인과
  사용자/run 잠금·현재 token 검사는 유지하므로 재예약된 옛 실행은 여전히 거절된다.
  실제 유료 dispatch만 heartbeat·lease 시간·현재 동의·소스가 모두 유효해야 한다.
- 옛 RPC 이름과 인자는 유지한다. 옛 Edge가 만든 NULL lease 행은 원래 흐름대로 동작한다.
  기존 행과 옛 Edge의 새 행은 dispatch 여부가 불명확하므로 보수적인 표시 기본값을 둔다.
  v2가 그 행을 재예약하지 않는다. 옛 dispatch/finish/audit_attempt는 v2 lease 행을 바꿀 수 없다.
- 0236/0237/0238/0244는 수정하지 않았다. 기존 run owner/cascade와 감사 삭제 규율을 그대로 사용하므로
  삭제 등록부를 늘리지 않는다. v2 네 함수도 definer/search_path·service_role 전용 GRANT를 지킨다.

| tier/spend/capacity/일시 RPC 실패, 모델 설정 오류 | 허용 | dispatch 없음. finish(null) → pre_dispatch_failed |
