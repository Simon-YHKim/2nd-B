# D6 보안 후속 수정 · 2026-10-15

**구현자 회귀 검사 결과이며 독립 보안 PASS가 아니다.**
[이전 인수](D6-PHASE1-261008.md)의 보안 BLOCK 6건을 수정한다.
0225/0226 운영 적용·새 앱/프록시 RPC 연결은 계속 보류한다.

## 범위와 운영 확인

사용자의 전체 잔여 작업 완료 지시와 안전 우선 결정을 따른다. 인터뷰 저장과 AI 보류를
연결하기 전에 기존 원장의 보안 지적을 닫는 선행 작업이다. 시기 카드 원장이나
클라이언트의 직접 coverage 쓰기 권한 회수는 이 변경에 포함하지 않는다.

2026-10-15 운영 migration ledger·catalog를 읽었다. 0225/0226은 미적용이고
`interview_sessions`·`interview_transcripts`·`interview_transcript_turns` 및
`records.interview_ai_hold`가 없다. 운영에 한 번도 적용되지 않은 0225 후보와
그 데이터 보존 롤백을 수정했다. 새 운영 migration 번호를 예약하거나 DB에 쓰지 않았다.
배포 시에는 당시 ledger를 재확인하고 운영용 timestamp 버전을 부여해야 한다.

## 판정·담기 순서와 다음 연결 조건

- writer와 commit은 같은 계정·세션 잠금으로 직렬화한다. red writer가 먼저면 담기는
  coverage를 더하지 않는다. commit이 먼저면 이미 적립한 값은 과거 합계로 유지하고,
  늦은 red는 남은 기록과 대화록의 AI 보류를 올린다. 적립을 되감거나 재적립하지 않는다.
- 레코드 또는 대화록 행을 다른 쓰기가 잠갔으면 writer는 `interview_record_busy_retry`
  (40001)를 반환한다. 앱·프록시 연결 단계에서 **판정 기록을 재시도하고 확정하기 전까지
  AI 처리로 넘기지 않는 계약**이 필요하다. 현재는 새 RPC 호출부가 없으므로 연결 완료가 아니다.
- 원장의 hold를 다른 AI 입력 경로에 연결하는 T28은 별도 잔여 작업이다. 이 PR만으로
  임베딩·후속 질문·일반 기록 읽기까지 모두 차단된다고 보고하지 않는다.
- pg_cron의 고유 키는 jobname+username이다. 현재 DB 필터만 붙이면 `schedule()`이
  같은 사용자의 다른 DB 예약을 덮어쓸 수 있어, 그런 충돌은 트랜잭션 전체를 중단한다.

## 검증 방법과 한계

운영과 분리한 Docker PostgreSQL 16.15에서 수행했다. 기존 CI의 pgvector 이미지로 시작했고,
실제 cron 검사를 위해 pg_cron 1.6을 설치하면서 PostgreSQL 패키지는 16.15가 됐다.
예약 실행은 `cron.launch_active_jobs=off`로 두었다. 운영 PostgreSQL은 17.6이며
이번 로컬 결과를 운영 실행 증거로 바꾸지 않는다.

- 새 `db/tests/interview_transcript_ledger_security.py`: 잘못된 red, 늦은 red,
  담기와 판정의 양방향 경합, 소유자·기록 키, 프로필 삭제, 롤백 coverage,
  삭제 경합과 롤백 후 삭제 경합의 8개 묶음. CI scratch lane에도 연결했다.
- 실제 cron 검사는 같은 스크립트의 `--cron-only`이다. pg_cron이 없는 CI에서
  가짜 표로 대신 PASS를 만들지 않는다. 로컬 실제 확장으로 직접 검사했다.
- 기존 SQL 회귀, 데이터 보존 롤백 왕복, 7개 동시성 묶음을 재실행했다.
- `npm run verify`: 1,113개 묶음·18,364개 통과·1개 건너뜀. 최종 SQL 트리를
  별도 새 DB에 CI 고정 버전 Supabase CLI 2.116.0으로 처음부터 적용했다.
- 실제 LLM 호출·운영 적용·앱 연결·기기 검사는 이 SQL 변경에서 수행하지 않았다.

완료 조건은 최신 커밋 CI·독립 검토 PASS·새 중간 지적 0이다. 같은 PR이 3회 BLOCK이면
사용자 결정대로 멈춰 보고한다. 과거 1단계의 예외 머지를 새 작업에 자동 적용하지 않는다.
