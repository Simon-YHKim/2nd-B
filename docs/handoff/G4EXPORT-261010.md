기존 authenticated의 소유자 SELECT는 유지하므로 제외 칸은 이번 서비스 내보내기 범위에서만 빠진다.

## 바뀌는 동작과 계약

- `EXPORT_TABLES`의 기존 descriptor 방식으로 `fk: user_id`, 명시적인 8칸 `select`,
  `created_at ASC, id ASC` 정렬을 사용한다. 활성·취소 이력을 모두 싣고 없으면 빈 배열이다.
- 결과 키는 `tables.profile_context_imports`. `schema_version: 1`, JSON 파일명,
  소유자 재확인·페이지 나눔·용량 한도·실패 시 전체 오류 응답은 그대로다.
- 운영에 0243 없이 새 exporter만 배포하면 SELECT가 거절되어 전체 export가 503으로 실패한다.
  `check-edge-function-schema-deps.mjs`가 표 존재에 더해 8개 칸의 존재와 실제
  `service_role SELECT`를 확인하도록 했다. 배포 워크플로의 기존 schema gate가 배포 전에 실행한다.
- `db/erasure-registry.json`과 0240의 `retained` 분류, 소유자 FK cascade,
  `service-contract-erasure-entries.json`의 0242 `field_undo` 삭제 정책은 바꾸지 않는다.
  새 표·칸·삭제 정책이 없으므로 등록부 추가나 0240 재생이 필요하지 않다. 회귀 테스트로 고정했다.
- 개인정보처리방침은 콘텐츠·프로필·사용 이력과 내보내기 권리를 범주로 안내하고 표를 열거하지 않는다.
  삭제 안내도 내보내기 진입 경로만 안내한다. 새 수집·목적·보관 변경이 없어 두 문서는 그대로 두었다.
  표 범위를 서술하는 DPIA와 프로필 가져오기 안내는 갱신하고 exporter의 밀린 코드 인용도 대조했다.
  UI와 로케일 키 변경은 없다.
